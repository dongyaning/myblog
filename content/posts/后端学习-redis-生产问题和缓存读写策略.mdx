# 缓存雪崩

缓存雪崩是指缓存中的大量数据同时失效（如过期）或服务器宕机，大量请求涌入数据库，导致数据库过载。

原因主要有两种：

## 大量数据同时过期

如给大量数据设置了同一个过期时间，就可能会发生缓存雪崩。

### 解决方案

1.  直接地，在设置时不要让很多数据的过期时间一样，比如加个随机数。
2.  业务线程加互斥锁，保证同一时间只有一个请求去构建缓存（去数据库读数据，放到缓存）。
3.  不设置过期时间，由后台线程主动去淘汰缓存数据。

## 服务器宕机

### 解决方案

1.  拒绝请求或限流。
2.  使用高可用集群，进行故障切换。

# 缓存击穿

和缓存雪崩类似，可以看成是缓存雪崩的一个子集。主要是考虑到被频繁访问的热点数据如果被淘汰了或过期了，这个时候大量的请求访问过来，也会给数据库造成很大压力。

策略也类似：

1.  业务线程加锁。
2.  热点数据不设置过期时间或及时更新。

# 缓存穿透

这个一般就是恶意攻击的情况，有大量不合理的查询，数据不在缓存，也不在数据库。虽然数据不在数据库，但是都被打到数据库了，数据库还是得处理，很有可能把服务弄崩。

解决方案：

1.  数据库查询不存在时缓存空值或无效 key，并设置过期时间（不宜过长）。
2.  布隆过滤器，hash + bit 位，概率结果。不存在一定准确，存在不一定准确。理论上添加的元素越多，误报的可能性越大。
3.  接口限流，根据用户或者 IP 对接口限流，或拉黑名单。

## 布隆过滤器

就是K个哈希函数 + N位图

数据 -> 经过K个哈希函数得到K个哈希值 -> K个哈希值对N取模 -> 将位图对应位置设为1（或检查是否为1）。

因为存在hash冲突，所以K个位数不一定能保证数据存在，但是只要有一个不存在一定能保证数据不存在。

## 缓存预热方式

常见的缓存预热方式有两种：

1.  **使用定时任务**，比如 xxl-job，来定时触发缓存预热的逻辑，将数据库中的热点数据查询出来并存入缓存中。
2.  **使用消息队列**，比如 Kafka，来异步地进行缓存预热，将数据库中的热点数据的主键或者 ID 发送到消息队列中，然后由缓存服务消费消息队列中的数据，根据主键或者 ID 查询数据库并更新缓存。

# 缓存双写一致性

针对缓存双写一致性，主要要针对写操作。

对于**读操作**，逻辑基本是固定的：缓存命中则返回，不命中则读取数据库，更新缓存并返回。

写操作可以有如下尝试：

- 先更新数据库，后更新缓存

- 这种方式存在并发问题，两个写操作并发时可能会引发数据不一致。

- 先更新缓存，后更新数据库

- 同上，逻辑类似。

- 先删除缓存，后更新数据库。

- 这种方法在**读写并发**时也可能会引发数据不一致问题。写操作先删除缓存，读操作缓存不命中，并更新缓存，写操作更新数据库。此时缓存中的数据没被删除，且为旧值。
- 解决方案可以是：延迟双删。上面的问题就是并发问题导致缓存没被删除，那么就可以延迟一段时间，再删一次。
- 延迟双删对于一致性的效果较好，但是延迟时间的设置是个玄学（大问题），数据库操作时间不确定，有的操作耗时长，很难设置固定时间覆盖所有情况。

- 先更新数据库，后删除缓存（推荐，主流）

- 这种方案也会在读写并发时出现不一致问题，但是出现的概率很低。因为出问题的场景是写操作更新完数据库之后，读操作缓存不命中，读取数据库并更新缓存，写操作再删除缓存。但是缓存的更新速度很快，这个情况很难发生。所以这个方案的整体表现和性价比都是比较好的，实现也简单。
- 但是这个方法也会出现问题，就是**第二步删除缓存的操作可能会失败**。

- 解决方案：

- 缓存设置过期时间保底
- 读写锁
- 消息队列（或数据库binlog + 消息队列）

## 更高一致性需求场景

- 分布式锁

- 持有锁期间，执行 “更新数据库 + 删除缓存”。
- 增加了锁的开销，降低了并发性能，适合一致性优先于性能的场景。

- 通过binlog + 消息队列保证“最终一致性”

- 和业务代码解耦。
- 过程中可能会存在不一致。

### 总结：如何选择策略？

双写一致性没有 “银弹方案”，需根据业务场景平衡一致性、性能和复杂度：

- **普通业务（允许短暂不一致）**：优先选择 “先更新数据库，再删除缓存”，配合删除重试机制；
- **并发高 + 更新频繁**：避免分布式锁，可搭配 “延迟双删” 减少脏数据概率；
- **核心业务（强一致性要求）**：使用 “分布式锁 + 先更数据库再删缓存”，牺牲部分性能换取一致性；
- **大规模系统（解耦优先）**：采用 “binlog 异步同步”，通过 Canal 等工具实现缓存与数据库的最终一致。

# 关于缓存读写策略的新总结 ※

![62d46814edf3d74b6499883656d427e7.png](/images/posts/后端学习-redis-生产问题和缓存读写策略/生产问题和缓存读写策略-2.png)

其实大部分场景都可以用[先更新数据库，再删除缓存]，这个叫旁路缓存。

这个方案发生不一致的场景为：

```latex
读写并发：
读：缓存不命中，读取数据库
写：更新数据库，删除缓存
读：更新缓存（旧值）

// 这种情况发生的概率很低，因为 2,3 发生在 4 前面，这种可能性是很小的。
// 4是更新缓存，2，3要读取数据库再更新缓存。4要比2,3快得多！

这里要注意，在分布式系统中，redis集群，主从架构下，这个不一致发生的并不罕见，因为存在主从延迟。
读可能是读的从库。因此在分布式系统下，旁路缓存 + 其它策略如延时双删或消息队列等还是很有必要的。

我这里补充一点：新数据提交之后，读的就一定是新值了，即使还没刷盘。因为innodb读的时候也是先去
buffer poll 里面读的。
```

如果对于一致性要求很高，避免上面这种不一致的发生，可以使用延时双删：

```latex
updateDB()
deleteRedis()
sleep(x) // 考虑主从延迟推荐0.5-1s
deleteRedis()

// 休眠的这段时间，那个读进程一般来说都执行完了，这个时候再删一次，
// 可以解决这种不一致（短暂不一致可接受）。
```

如果考虑到缓存删除失败的问题，可以引入[消息队列]，失败了重复尝试。

```java
updateDB();
if (!redis.delete(key)) {
    mq.send(RetryDeleteCacheMessage); // 异步重试
}
// 生产级配置，很多公司如美团、阿里都用这种方式保证缓存的最终一致性。
```

如果希望一致性更高，也可以考虑不用缓存（并发量数据库能承受的话）。

对于类似阅读量这种写多读少的数据，而且没那么重要，对于一致性要求没那么高的。可以使用Write-Behind方案。也就是直接更新缓存，再通过消息队列或线程池批量异步更新数据库。

对于 write-through 写穿透，几乎没人用Redis做真正的写穿透。因为要实现跨系统（Redis，Mysql）的事务成本极高。

强一致性的正确做法：

- 如果数据**只存在 Redis**（如秒杀库存），用 Lua 保证原子性
- 如果数据**必须持久化到 DB**，且要求强一致：

- 方案1：**不用缓存**，直接操作 DB（加数据库行锁）
- 方案2：**用 DB 作为唯一数据源**，缓存仅作读优化（即 Cache-Aside + 高可靠删除）
