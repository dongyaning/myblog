# 基本概念

![image.png](/images/posts/计算机基础-计算机网络-tcp-传输层-70cf29/tcp-传输层-1.png)

这块简单说一下，这个报文格式肯定是比较关键的。

注意几个不太明显可以理解的点：

- 序列号：随机数作为初始值，每次发送数据都累加数据的字节数，解决包乱序。
- 应答号：下一次期望收到的数据的序列号，解决丢包。
- 控制位：

- ACK为1：确认应答字段变为有效，TCP规定除了最初的SYN包，此值恒为1。
- RST为1：出现异常强制断连。
- SYN为1：建立连接。
- FIN：希望断开。

TCP三大特点：面向连接，可靠、字节流。

关于UDP就是啥也不提供，以数据包的形式发送数据，首部固定八个字节，拥塞控制不提供，可靠也不管，有序性也不管，适合DNS这种小包或者是传输音频，视频流啥的。

TCP只能是一对一，UDP可以N对N，可以广播。

TCP和UDP可以使用同一个端口，分发给两个模块。

# 连接建立

三次握手

![image.png](/images/posts/计算机基础-计算机网络-tcp-传输层-70cf29/tcp-传输层-2.png)

第三次握手客户端可以携带数据，前两次不行。

## 为什么是三次握手？

总结就是两次不行，四次没必要。

两次为什么不行，主要有原因：

- 第一个就是三次才能双方都各收发一次，验证双方的收发能力。
- 和第一个类似，因为序列号很重要，必须要三次握手才能确认双方的序列号。序列号可以去重，排序，判断哪些对方已经收到了。
- 再就是历史连接问题，场景“客户端发送的第一个连接请求（SYN1）因网络延迟而滞留，于是客户端重发了第二个请求（SYN2）并成功建立了连接，数据传输完毕后连接被释放。此时，延迟的 SYN1 才到达服务端。”。

- **如果是两次握手：**服务端收到这个失效的 SYN1 后，会误认为是一个新的连接请求，并立即分配资源、建立连接。但这将导致服务端单方面维持一个无效连接，白白浪费系统资源，因为客户端并不会有任何响应。
- **如果是三次握手的：**在第三次握手的时候就可以发现不对了，就不会建立连接。

## 半连接队列和全连接队列

在 TCP 三次握手过程中，服务端内核会使用两个队列来管理连接请求：

1.  **半连接队列**（也称 SYN Queue）：当服务端收到客户端的 SYN 请求并回复 SYN+ACK 后，连接会处于 SYN_RECV 状态。此时，这个连接信息会被放入半连接队列。这个队列存储的是尚未完成三次握手的连接。
2.  **全连接队列**（也称 Accept Queue）：当服务端收到客户端对 ACK 响应时，意味着三次握手成功完成，服务端会将该连接从半连接队列移动到全连接队列。如果未收到客户端的 ACK 响应，会进行重传，重传的等待时间通常是指数增长的。如果重传次数超过系统规定的最大重传次数，系统将从半连接队列中删除该连接信息。

半连接队列是 SYN 泛洪攻击所针对的目标，就是一直发第一次握手的 SYN，把半连接队列占满。

## 网络层IP能分片，为什么传输层TCP也要根据MSS分？

- MSS：除去IP和TCP头部，网络包能容纳的TCP数据的最大长度。
- MTU：就是网络包的长度，IP包。以太网1500 B。

之所以传输层还要分片，是因为IP没有重传机制啥的。如果只在IP分片，掉了一个就得重发所有的（同一个 TCP 包的）。

## 第一次握手丢失

那就重传，超时重传的超时时间操作系统写的，这个时间会越来越长，到某一个阈值次数就不传了。

## 第二次握手丢失

双方都会重传，这个也好理解。对于客户端来说，二次握手丢了，他感觉自己的报文丢了。服务端没收到第三次握手，他也感觉自己的报文丢了，所以都会重传。

## 第三次握手丢失

客户端发出去了就认为连接建立完了。

服务端还是会重发第二次的，因为他没收到回复。

## SYN 攻击

就是伪造大量客户端只发第一次的握手，这样操作系统会把这个东西放到一个叫做半连接队列的数据结构中，这个满了就没法为正常用户服务了。

应对方法：

- 减少重试次数
- 增大半连接队列
- syncookies

- 这个比较好，操作系统提供的另一个方法，可以绕过半连接状态，就是直接生成一个cookie用这个来握手，成功了就直接放到 accept 队列里边。
- 开启通过 设置 net.ipv4.tcp_syncookies = 1 （半连接队列满时启用）

# 连接断开

四次挥手

![image.png](/images/posts/计算机基础-计算机网络-tcp-传输层-70cf29/tcp-传输层-3.png)

**主动关闭连接的一方，才会有 TIME_WAIT状态。**

## WHY 四次

比如说客户端先 FIN，这表示：客户端不发了，但是还可以接收。这个时候服务器可能还没发完。

只有服务器也发 FIN，也不发了。双方都不发了，才算完了。

## 第一次挥手丢失

重试，几次不行就直接关

## 第二次挥手丢失

**这个挥手和握手都是，ACK不会重传！**

ACK丢了，那还是客户端重试，几次不行就关。

客户端进入WATE2之后，这个状态有时间限制，如果服务器一直不关，客户端就直接关了。

## 第三次挥手丢了

服务端这个时候处于CLOSE_WAIT，然后发FIN丢了，会重试，如果几次不行再等一会还不行，服务器就直接关了。

服务器关了之后，这个时候客户端是WATE2，超时了客户端也就关了。

## 第四次挥手丢了

服务端还是差不多，因为他还是认为他的第三次那个FIN丢了，他会重发，试几次不行就关。

对于客户端，他发了ACK就开启一个定时器，过了那个时间他就关，如果再次收到FIN就重置定时器。

## TIME_WAIT的设计目的

这个2MSL，相当于允许最后的ACK丢一次，如果丢了，对面会重发 FIN，要不然直接 close 的话，对面重发 FIN 就会回复一个 RST 复位报文，这会被 Server 认为是一个连接错误。等 2MSL 可以第一个 ACK 丢失时再回复一个 ACK，保证另一方可以顺利进入 Closed 状态。

此外，序列号不是递增，到了最大值会为0，所以无法通过序列号大小判断新老数据。

还是那个历史连接的问题，网络传输是不稳定的，有些数据包可能会在某个路由器里“迷路”一会儿，过很久才到达，如果没有 TIME_WAIT，发了 ACK 就直接关闭，紧接着新建了一个连接，这个时候那个迷路的数据包又到了，就有可能被认为是当前会话的数据。

等了2MSL之后，可以确保前面的连接发的包肯定已经消失了。MSL是包在网络中的最大存活时间。TTL是最大路由跳数。

**总结来看，两个作用：\*\***确保被动方收到最后一个 ACK、解决历史连接问题\***\*。**

正常流程（序列号确认机制）：

如果丢了就需要重传。

## 超时重传

数据包丢失 / ACK丢失。

**超时时间**的设置是一个需要考量的值。RTT是往返时延，这个超时时间要参考这个时延，尽量比它稍微大一点。

超时时延过大会导致网络利用率降低，过小可能ACK还没回来就又发。

因为网络情况是不断变化的，所以这个超时时间也应该是不断变化的，总之就是采样真实RTT和其变化用某种算法确定这个值，而且**每次重传时延都加倍**（网络状况不好）。

但是这个有点慢，所以就有了**快速重传**。

## 快速重传

![image.png](/images/posts/计算机基础-计算机网络-tcp-传输层-70cf29/tcp-传输层-5.png)

三个重复ACK。

但是要重发那一个还是后面所有的？好像都不太好。

于是就有了**SACK**。

## SACK

就是ACK的时候带上收到的信息。这样对方就可以知道哪些收到了，哪些没收到，只重发没收到的即可。

linux下，打开 net.ipv4.tcp_sack。Linux 2.4后默认打开。

## 滑动窗口

为了解决性能问题，用窗口可以一次性发几个，不用等待ACK再发，而且可以通过窗口管理发送流量什么的。

累计确认（累计应答）这个你知道的，就是ACK=X+1，代表X及其前面的都收到了。

窗口大小一般由接收端的接收能力决定，接收端会在TCP传Window字段回去，也就是窗口大小。发送方的窗口不能比这个大。

**误区纠正：**

- 发送端不等于客户端
- 接收端不等于服务端

TCP 是全双工，**两端各有一个发送缓冲区与接收缓冲区，两端都各自维护一个发送窗口和一个接收窗口**。接收窗口大小取决于应用、系统、硬件的限制（TCP 传输速率不能大于应用的数据处理速率）。通信双方的发送窗口和接收窗口的要求相同。

# 流量控制

就是上面说的 Window 字段。

**在 TCP 连接中，任意一方在发送 ACK（或数据）时，都会在 TCP 头部的** `**Window**` **字段中通告自己当前的接收窗口（rwnd），告诉对方“你现在最多能发多少数据给我”。对方据此动态调整自己的发送窗口大小。**

反正就是通过滑动窗口 + Window 字段实现的。

先收缩窗口，过段时间再减少缓存。

## 窗口关闭

窗口为0之后，就是关闭了。如果这个时候对面给出的改变窗口大小报文丢失了。那就死锁了。所以一旦有0窗口，就会启动一个计时器，到时间了就询问一下窗口。

# 拥塞控制

流量控制是收发双方来说的，而拥塞控制是考虑整个网络的情况（根据超时重传/快速重传的情况来衡量网络情况）。

方式是：发送方维护 拥塞窗口cwnd。 **发送窗口 = min (拥塞窗口，接收方接收窗口，就是 TCP 首部的 Window)**。

只要出现了超时重传/快速重传，就认为出现了拥塞。

拥塞控制算法：

- 慢启动
- 拥塞避免
- 拥塞发生
- 快速恢复

## 慢启动

初始 cwnd = 1 (MSS，后面也都是 MSS) 发送方每收到一个ACK，cwnd + 1。 直到 ssthresh。 cwnd >= ssthresh 时，使用拥塞避免算法。

## 拥塞避免算法

每收到一个ACK，cwnd 增加 1/cwnd。即线性增长。这里要注意哈，这个地方说的是一个 ACK 增加 1/cwnd 个 MSS。

实际上就是，在 window >= cwnd 且 网络无丢包的情况下，同时可以发送 cwnd 个报文段，一个 RTT 就会收到 cwnd 个 ACK，cwnd 就会+1。所以基本上还是一个 RTT，cwnd + 1 MSS，这是不矛盾的。

## 拥塞发生

就是出现重传了，类型不一样，处理不一样。

### 超时重传造成的

这个时候比较严重，超时了，说明网络拥塞厉害。

ssthresh = cwnd / 2

cwnd = 1

进入慢启动。

### 快速重传造成的

还能收到 3 个ACK，还行。

cwnd = cwnd / 2

ssthresh = cwnd（就是原来 cwnd 的一半，这两个表达式是顺序的）

进入快速恢复。

## 快速恢复

cwnd = ssthresh + 3 \* MSS

之后每收到一个重复ACK，cwnd + 1 \* MSS （窗口膨胀期）

当来了新的ACK，有推进了，cwnd = ssthresh，退出快速恢复（窗口回退）。

# TCP vs UDP

| 特性         | TCP                        | UDP                                 |
| ------------ | -------------------------- | ----------------------------------- |
| **连接性**   | 面向连接                   | 无连接                              |
| **可靠性**   | 可靠                       | 不可靠 (尽力而为)                   |
| **状态维护** | 有状态                     | 无状态                              |
| **传输效率** | 较低                       | 较高                                |
| **传输形式** | 面向字节流                 | 面向数据报 (报文)                   |
| **头部开销** | 20 - 60 字节               | 8 字节                              |
| **通信模式** | 点对点 (单播)              | 单播、多播、广播                    |
| **常见应用** | HTTP/HTTPS, FTP, SMTP, SSH | DNS, DHCP, SNMP, TFTP, VoIP, 视频流 |

## TCP / UDP 选择

当数据准确性和完整性至关重要，一直都不能出错，通常选择 TCP。如 Web 浏览，文件传输，邮件收发，远程登录。

当实时性、速度和效率优先，且能容许少量数据丢失或乱序时，通常选择 UDP。如实时音视频通信，在线游戏，DHCP，IoT 数据上报。
