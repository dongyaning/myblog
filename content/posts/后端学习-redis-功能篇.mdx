# 过期删除策略

## 过期时间设定

```shell
set <key> <value> ex <n> ：设置键值对的时候，同时指定过期时间（精确到秒）；
set <key> <value> px <n> ：设置键值对的时候，同时指定过期时间（精确到毫秒）；
setex <key> <n> <valule> ：设置键值对的时候，同时指定过期时间（精确到秒）。（这个只有字符串有哈）
expire <key> <n> (所有对象都可以用这个设置)

// 查看过期时间
ttl key    // 过期时间为-1表明永不过期
// 取消过期时间
persist key

```

## 过期判定

所有设置了过期时间的键值对，redis都会将其用一个字典（哈希表）存储起来。字典的键是指向key的指针，值是过期时间。

```c
typedef struct redisDb {
    ...

    dict *dict;     //数据库键空间,保存着数据库中所有键值对
    dict *expires   // 过期字典,保存着键的过期时间
    ...
} redisDb;

// expires 是一个哈希表，key 是原 key 的指针，value 是一个整数（过期时间戳）
```

每次客户端请求某数据时，会先判断是否在过期字典里，如果在的话，判断当前系统时间是否大于等于过期时间，如果是，则过期。

## 过期删除策略

判断某键值对过期之后，有几种删除策略：

- **定时删除：**到时间就删。内存友好，CPU不友好。
- **惰性删除：**每次访问的时候检查到过期了才删。CPU友好，内存不友好。
- **定期删除：**每隔一段时间随机取出来一些检查一下。折中，但是平衡点难掌握。

Redis实现选择的是 **惰性删除 + 定期删除**。

惰性删除好说，就是每次访问的时候检查一下，至于是异步删除还是同步，可以配置。

定期删除，就是每次随机取出来20个数据，检查一下，如果过期比例超过25%就再取20个，这个过程的时间上限为25ms。同时，如果执行时间大于某个阈值，就中断这一次的定期删除，以避免占用过多的CPU资源。

```latex
# 定期删除执行频率，默认为 10，就是一秒十次。
hz 10
# 在hz基础上计算一个动态值，默认开启
dynamic-hz yes
```

# 内存淘汰策略

Redis的内存淘汰策略有八种，可以分为两类：

1.  不进行数据淘汰：

1.  **no-eviction：\*\***redis4之后默认的方式\*\*，就是内存不够了就报错，不删除。

1.  进行数据淘汰：

1.  在设置了过期时间的数据中进行淘汰：

1.  **volatile-random：**随机淘汰设置了过期时间的任意键值；
1.  **volatile-ttl：**优先淘汰更早过期的键值。
1.  **volatile-lru（\*\***Redis3.0 之前，默认的内存淘汰策略\***\*）：**淘汰所有设置了过期时间的键值中，最久未使用的键值；
1.  **volatile-lfu（**Redis 4.0 后新增的内存淘汰策略）：淘汰所有设置了过期时间的键值中，最少使用的键值；

1.  在所有数据范围内进行淘汰：

1.  **allkeys-random：**随机淘汰任意键值;
1.  **allkeys-lru：**淘汰整个键值中最久未使用的键值；
1.  **allkeys-lfu（Redis 4.0 后新增的内存淘汰策略）：**淘汰整个键值中最少使用的键值。

## 设置内存淘汰方式

```shell
// 临时设置，无需重启，但重启后失效
config set maxmemory-policy <策略>

// 持久设置，需要重启生效，修改配置文件
maxmemory-policy <策略>
```

## LRU(Least Recently Used)算法和LFU（Least Frequency Used）算法

**LRU是最近最少未使用**，具体实现通过哈希表+双向链表。redis实现的LRU是近似的，在数据中存储了一个最后访问的时间戳字段。每次淘汰的时候随机取5个，淘汰时间戳最早的。

LRU的一个问题就是无法解决缓存污染，即一次性读入大量数据之后，即使这些数据是一次性的，依然会长时间保留在缓存中。

**LFU是最近最不常用。**这个算法的淘汰过程是考虑的数据访问频率。通过在数据中记录最后访问时间戳以及访问频率（这个频率不只是次数，也跟时间有关）。

具体实现上，LRU和LFU的结构没有区别，只是LRU是吧lru字段的全量当做时间戳，而LFU则是将lru分为两个部分：高16位表示时间戳，低8位表示频率。

Redis 在访问 key 时，对于 logc 是这样变化的：

1.  先按照上次访问距离当前的时长，来对 logc 进行衰减；
2.  然后，再按照一定概率增加 logc 的值。

可以通过配置文件中的 lfu-decay-time 和 lfu-log-factor 来调整 衰减速度 和 增长速度。

# 基于Redis实现延时任务

一如：

- 订单在 10 分钟后未支付就失效，如何用 Redis 实现？
- 红包 24 小时未被查收自动退还，如何用 Redis 实现？

Redis 中无非就两种方案：

1.  Redis 过期事件监听。
2.  Reddisson 内置的延时队列

## 过期事件监听（不推荐）

这个是基于Redis2.0引入的发布订阅功能。

![image.png](/images/posts/后端学习-redis-功能篇/功能篇-2.png)

Redis中有一些默认的channel，其中\_\_keyevent@0\_:expired就是监听key的过期事件，key过期之狗，Redis会发布一个key过期事件到这个channel。

### 过期事件存在的问题

1.  时效性差。

1.  因为这个事件不是过期之后就发，而是删除key的时候才发。上面讲了删除不是立马删除的，所以存在一定的时延，还不小。

1.  丢消息

1.  没有持久化，如果没有订阅者就直接丢了。

1.  多服务实例下消息重复消费

1.  因为消息是广播的，所以这里还得自己实现一下不重复消费的逻辑。

## Redisson延时队列

Redisson 的延迟队列 **RDelayedQueue** 是基于 Redis 的 SortedSet 来实现的。Redisson将需要延迟执行的任务插入到 SortedSet 中，并给它们设置相应的过期时间作为分数。

Redissson定期扫描过期元素，过期的移除并加入到就绪消息列表，就绪消息列表是一个阻塞队列，有消息进来就会被消费者监听到。

RDelayQueue 中的消息会被持久化，且所有客户端都从同一队列取消息，不存在重复消费的问题。

### Redisson 是什么

- **Redisson** 是一个 **Java 编写的 Redis 客户端库（Client Library）**；
- 它运行在你的 **Java 应用程序中**，用来和 Redis 服务器通信；
- 它在 Redis 原生命令基础上，封装了 **面向对象的 API** 和 **高级分布式功能**（如分布式锁、布隆过滤器、延迟队列等）；
- 你必须先有 Redis 服务，才能使用 Redisson。

📌 **Redisson 是客户端（Client）**，是 **Java 程序访问 Redis 的一种工具**。
