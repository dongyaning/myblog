# 基本概念

HTTP ，超文本传输协议（HyperText Transfer Protocol）

拆分超文本、传输、协议。超文本指的是两层意思：1. 超越文本，它是文字、图片、视频等的混合体 2. 最关键有超链接，可以从一个超文本跳转到另一个超文本。HTTP就是最常见的超文本。

总结来看，**HTTP是一个在计算机世界里专门在两点之间传输文字、图片、音频、视频等超文本数据的约定和规范。**

## 状态码

- 1xx：提示信息，是协议处理的一种中间状态，较少用到。

- 比如 http 升级 websocket 的时候服务器就会返回 101 状态码。

- 2xx：服务器成功处理

- 200 OK，最常见，一切正常，会有body数据。
- 202：服务端已经收到了请求，但是还未处理。
- 204 No Content，成功，但响应没有body，比如删除一个什么东西，只返回一个结果。
- 206 Partial Content，HTTP分块下载的断点续传，表示返回的资源不是全部，只是一部分。

- 3xx：重定向

- 301 Moved Permanetly：永久重定向，资源不在了。
- 302 Found：临时重定向，临时需要访问另一个URL。
- 304 Not Modified：不具有跳转含义，表示资源未修改，告诉客户端可以继续使用缓存资源。

- 4xx：客户端报文有误错误，服务器无法处理

- 400 Bad Request：笼统表示客户端报文有误
- 403 Forbidden：服务器禁止访问，非客户端出错。
- 404 Not Found：资源在服务器上未找到。

- 5xx：服务器内部错误

- 500 internal Server Error：笼统错误。
- 501 Not Implemented：客户端请求的功能还不支持。
- 502 Bad Gateway：这是网关或代理发的，网关本身正常，访问后端服务器时发生错误。
- 503 Service Unavailable：服务器忙，暂时无法响应。

## 常见字段

- Host：服务器域名
- Content-Length：回应的数据长度
- Connection：指定长连接等连接方式

- HTTP 1.1默认长连接，为了兼容1.0，需要指定 Connection: Keep-Alive

- Content-Type：服务器回应的数据格式。

```plain
Content-Type: text/html; Charset=utf-8

客户端可以使用 Accept 声明自己接受的数据格式。
Accept: */*
```

- Content-Encoding：数据的压缩方法

- 同理，客户端用 Accept-Encoding 指定能接受的压缩方法。

## GET 和 POST

GET语义是从服务器获取指定资源，GET请求的参数一般在URL中，URL只能传ASCII，所以GET也是。浏览器会对URL长度做限制（HTTP没有限制）。安全且幂等。GET也是可以带body的，只是一般不会这么做。

POST语义是根据请求负荷对指定的资源做出处理。body中的数据可以是任意格式，CS双方协商好即可。非安全非幂等。URL也可以带参数。

安全：是否破坏服务器资源。

幂等：多次请求是否一致。

## HTTP缓存

具体不讲，好理解。

两种，强制缓存 和 协商缓存。

### 强制缓存

就是只要缓存还没过期，就用缓存的。

过期时间是在HTTP响应头的 Cache-Control 或 Expires 中指定的，都指定前者优先级高，也建议用前者。

状态码 200 (from disk cache)

### 协商缓存

就是之前状态码为 304 的那种状态，服务器告诉客户端可以用本地缓存的数据。

要注意一点：**强制缓存过期了，没命中，才能用协商缓存。**

实现上就是一开始服务端返回的时候协议一个字段，客户端再请求的时候带上，服务器检查资源是不是改了，没改就返回304。有两种实现：  
第一种：请求头 If-Modified-Since 和 响应头Last-Modified，这两个就是表示最后修改时间，比较好理解。

第二种：请求头 If-None-Match 和 响应头 ETag，这个也类似，只不过是基于资源的唯一标识，不是时间。这种更加准确，避免时间篡改等问题。

如果ETag和Last-Modifed都带上发过去了，那么ETag的优先级更高。这是因为：

- 时间的那个精度是秒级的，而唯一标识精度要更细。
- 有些服务器不能精确获取文件的最后修改时间。
- 最后修改时间改了，文件内容未必改了。

## HTTP特性

HTTP1.1， 2.0， 3.0，这里先介绍 1.1。

### HTTP/1.1 特点

HTTP/1.1 简单、灵活易于拓展（如HTTPS是在其上方引入了SSL/TLS安全传输层）、应用广泛跨平台（因为这玩意就是协议，谁都能实现）。

但是一体两面，因为HTTP是无状态的，减轻了服务器负担。但是一些需要关联性的操作就比较困难，虽然一般会用Cookie，这也相当于是对HTTP的扩展。

再者，明文传输，方便阅读，但是...毫无隐私可言。

最后，就是不安全：

- 明文传输，被窃取。
- 不验证通信放的身份，可能遭遇伪装。
- 报文完整性无法验证，遭遇篡改。

这一点可以通过 HTTPS 来解决哈。

### HTTP/1.1 性能

1.0 没有长连接，引入了**长连接**。

还有一个**管道网络传输**，基于长连接。就是客户端发了一个不用等回来就可以再发。但是服务端必须按顺序返回请求。客户端不阻塞，服务端堵塞。这个东西浏览器没实现，属于理论。

所以**队头阻塞**还存在，HTTP1.1性能一般。

### HTTP1.0 和 HTTP1.1 区别

- HTTP1.0 为短连接，1.1 支持长连接。
- **状态响应码** : HTTP/1.1 中新加入了大量的状态码，光是错误响应状态码就新增了 24 种。比如说，`100 (Continue)`——在请求大资源前的预热请求，`206 (Partial Content)`——范围请求的标识码，`409 (Conflict)`——请求与当前资源的规定冲突，`410 (Gone)`——资源已被永久转移，而且没有任何已知的转发地址。
- **缓存机制** : 在 HTTP/1.0 中主要使用 Header 里的 If-Modified-Since,Expires 来做为缓存判断的标准，HTTP/1.1 则引入了更多的缓存控制策略例如 Entity tag，If-Unmodified-Since, If-Match, If-None-Match 等更多可供选择的缓存头来控制缓存策略。
- **带宽**：HTTP/1.0 中，存在一些浪费带宽的现象，例如客户端只是需要某个对象的一部分，而服务器却将整个对象送过来了，并且不支持断点续传功能，HTTP/1.1 则在请求头引入了 range 头域，它允许只请求资源的某个部分，即返回码是 206（Partial Content），这样就方便了开发者自由的选择以便于充分利用带宽和连接。
- **Host 头（Host Header）处理** :HTTP/1.1 引入了 Host 头字段，允许在同一 IP 地址上托管多个域名，从而支持虚拟主机的功能。而 HTTP/1.0 没有 Host 头字段，无法实现虚拟主机。

### HTTP1.1 和 HTTP2.0 区别

- **多路复用（Multiplexing）**：HTTP/2.0 在同一连接上可以同时传输多个请求和响应（可以看作是 HTTP/1.1 中长链接的升级版本），互不干扰。HTTP/1.1 则使用串行方式，每个请求和响应都需要独立的连接，而浏览器为了控制资源会有 6-8 个 TCP 连接的限制。这使得 HTTP/2.0 在处理多个请求时更加高效，减少了网络延迟和提高了性能。
- **二进制帧（Binary Frames）**：HTTP/2.0 使用二进制帧进行数据传输，而 HTTP/1.1 则使用文本格式的报文。二进制帧更加紧凑和高效，减少了传输的数据量和带宽消耗。
- **队头阻塞**：HTTP/2 引入了多路复用技术，允许多个请求和响应在单个 TCP 连接上并行交错传输，解决了 HTTP/1.1 应用层的队头阻塞问题，但 HTTP/2 依然受到 TCP 层队头阻塞 的影响。
- **头部压缩（Header Compression）**：HTTP/1.1 支持`Body`压缩，`Header`不支持压缩。HTTP/2.0 支持对`Header`压缩，使用了专门为`Header`压缩而设计的 HPACK 算法，减少了网络开销。
- **服务器推送（Server Push）**：HTTP/2.0 支持服务器推送，可以在客户端请求一个资源时，将其他相关资源一并推送给客户端，从而减少了客户端的请求次数和延迟。而 HTTP/1.1 需要客户端自己发送请求来获取相关资源。

# HTTPS

![image.png](/images/posts/计算机基础-计算机网络-http-应用层/http-应用层-1.png)

**SSL/TLS 是一个东西的两个版本！ SSL已经被废弃了，TLS是它的升级版！现在都是用TLS。**

针对上面提到的HTTP明文传输造成的三种风险：被窃听、被篡改、被冒充。

HTTPS提出了相应的解决方案：

- 信息加密：无法被窃取。混合加密。
- 校验机制：无法被篡改。摘要算法，为数据生成独一无二的指纹，校验数据完整性。
- 身份证书：无法被伪装。将服务器公钥放入数字证书中。

## 混合加密

所谓混合加密，就是 对称加密 和 非对称加密 混合：

- 通信建立前，非对称加密交换 会话秘钥，后续就不再使用非对称加密。

- 非对称加密使用两个秘钥，公钥可以任意分发但私钥保密，解决了密钥交换问题单速度慢。

- 通信过程中全部使用 对称加密 的会话秘钥的方式加密密文数据。

- 使用一个密钥，速度快，密钥必须保密，无法做到安全的密钥交换。

## 摘要算法 + 数字签名

使用哈希值来判断内容是否被篡改。

![image.png](/images/posts/计算机基础-计算机网络-http-应用层/http-应用层-2.png)

这样可以保证哈希值不错的情况下，内容不会被修改。

但是，有可能出现哈希值和内容都被改了的情况！为了解决这个问题，使用 非对称加密算法。

### 非对称加密

公钥，私钥可以双向加解密，就是说，公钥加密，私钥可以解密，反过来也行。

下面就是比较有意思的点，也是**非对称加密的精髓**：

- **公钥加密，私钥解密。**可以保证内容传输的安全（这里说的是信息隐私问题，传输的信息不会被泄露，但还是存在整体被替换的风险，因为公钥是公开的，很好替换）。因为私钥是秘密，能持有私钥的才能解密实际的内容。
- **私钥加密，公钥解密。**可以保证消息不会被冒充。因为私钥是不可泄露的，既然能用公钥解密，就说明这个内容没被改过（如果是改了，那 hacker 也得用私钥加密，说明私钥泄露了，与前提矛盾），不然就解密不出来了，因为公钥和私钥是对应的。所以，只要公钥能正常解密，那么这个消息的来源一定是私钥的持有者。

所以**非对称加密的用途主要就在于通过 私钥加密，公钥解密 的方式，来确认消息的身份**，这就是数字签名算法。但是，私钥加密不针对内容，而是针对hash值。

## 数字证书

前面已经通过 哈希算法保证消息的完整性，通过数字签名来保证消息的来源可靠性（消息是从持有私钥的一方发出来的）。但是！持有私钥的（和公钥配对的）一定是服务器吗？？

未必，万一公钥和私钥都是被伪造的呢？（意思是你可以把客户端的公钥换成你的，然后用你的私钥对数据加密）。

为了防止公私钥这么容易被伪造，就需要一个权威机构，来颁发个证书，也就是CA。CA持有他自己的私钥，公钥是公开的，只要没人能伪造CA的私钥，就能用其公开的公钥来判断这个信息是不是对的。

私钥是服务端持有的，在服务端对数据用私钥进行加密，公钥要发给客户端用作解密。为了防止公钥被篡改，就需要CA来确认服务器的公钥。CA会把服务器的【个人信息 + 公钥 + 数字签名】打包成一个数字证书，其中数字签名是CA用自己的私钥对服务器的公钥做的加密。服务器把这个数字证书也给客户端。客户端收到之后，就可以用CA的公钥对数据解密，如果能解密成功，就说明这个证书是注册过的，是合法的，就可以取出来里面的公钥了。此时这个公钥就一定是服务器的公钥。就可以用这个公钥对数据解密了。

![image.png](/images/posts/计算机基础-计算机网络-http-应用层/http-应用层-3.png)

我补充一下数字证书和数字签名的区别：

数字证书包含数字签名，数字签名是基于数据证书的其它内容生成hash值，之后再用CA私钥加密得到的。相当于是一个密文签名，客户端可以用CA公钥解密这个签名，将得到的hash值和自己基于内容算的hash值对比，就可以知道是不是被篡改了。因为CA私钥是不公开的，所以也没人能伪造这个签名。

“CA 使用其私钥对证书内容的哈希值进行签名，生成数字签名，并将该签名附加到证书中。这个签名可用于验证证书的完整性和真实性，但**并未对证书本身进行加密**。”

这里还存在一个证书信任链的问题，有一些证书不是由根证书颁发的，而是下级证书，比如说百度的证书。而用户只信任根证书（这里的用户表示操作系统或浏览器），就需要根据下级证书中的签发者去CA请求上级证书，直到找到根证书。就可以用本地存的公钥去解码了。

浏览器信任根证书，根证书信任下级证书，所以浏览器也信任下级证书。人类用户信任浏览器，也就信任下级证书。

![image.png](/images/posts/计算机基础-计算机网络-http-应用层/http-应用层-4.png)

在现代网络安全体系中，TLS 的安全性不仅依赖于密码学协议的设计（如非对称加密、数字签名），更根本地依赖于一个“信任锚点”--即客户端内置的受信任根 CA 证书列表。**整个安全模型的前提是：这个信任锚点，这个信任根是安全的，未被篡改的**。在这里就是 **CA 的根证书**。

**操作系统会严格保护这个证书不会篡改**，只要这个证书是安全的，就可以安全地用这个证书验证数字签名是 CA 颁发的。就可以通过公钥解密其中的服务器公钥，就可以进行安全信息传输。

也就是说 先建立一个极难攻破的点，以这个点的安全为前提，密码学来保证后续流程的正确。

## 连接建立流程

SSL/TLS协议流程：

- 客户端向服务器索要并验证服务器公钥
- 双方协商产生会话秘钥 （前两步是 TLS握手阶段，也就是连接建立）
- 双方采用会话秘钥进行加密通话

这里具体的握手过程有两个算法：RAS 和 ECDHE。这个后面再详细说。

## 应用数据完整性

使用握手协议协商加密算法和生成对称密钥。

使用记录协议来保证应用程序数据的完整性。

## TLS握手过程

![image.png](/images/posts/计算机基础-计算机网络-http-应用层/http-应用层-5.png)

RAS属于密钥交换算法，因为在数据传输阶段时使用的对称加密，而对称加密的密钥不能泄露，所以通过密钥交换算法来对密钥进行非对称加密和交换。

### RAS 握手过程

RAS 密钥交换算法中，客户端会随机生成密钥，并使用服务端的公钥加密后再传给服务端，这样只有服务端才可以对加密数据解密，只要服务端的密钥安全。双方就此得到相同的密钥，后面就可以用这个密钥来加密应用消息了。

![image.png](/images/posts/计算机基础-计算机网络-http-应用层/http-应用层-6.png)

#### 第一次握手

客户端发送 Client Hello，打招呼。同时带上客户端使用的TLS版本号，以及生成的随机数，这个随机数是生成对称加密密钥的材料之一。同时还会发送支持的密码套件列表。

#### 第二次握手

服务端收到之后，确认TLS版本号是否支持，服务端也会生成一个随机数。同时从客户端提供的密码套件列表里面选一个合适的。

密码套件就是这样的格式（举例）：密钥交换算法 + 签名算法 + 对称加密算法 + 摘要算法。

经过两次握手，各种加密算法的版本已经被确定下来了。服务端还会在第二次握手返回时发送数字证书。

#### 第三次握手

客户端认证完证书，可信则继续握手。

客户端再生成一个随机数，用服务器的RAS公钥加密该随机数。

服务端收到解密，现在有三个随机数了，用这三个随机数，生成会话密钥，这个会话密钥，就是后面用于数据通信的对称加密密钥。

然后客户端发一个用生成的密钥加密的之前的总结，看看好用不，同时也是检查。

#### 第四次握手

服务端也试一下好用不。

就连接完毕了。

### RSA 缺陷

最大问题是不支持前向保密，因为传的随机数啥的都是公钥加密的，一旦私钥泄露，前面就全被看见了。

### ECDHE 算法基础

ECDHE 前向安全，被广泛使用，一般都是用这个。

#### 离散对数

![image.png](/images/posts/计算机基础-计算机网络-http-应用层/http-应用层-7.png)

a 和 p 公开，知道 i ，就可以算出来 b，但是知道 b，很难算出来 i。这是DH算法的数学基础，不深究了，直到结论就行。

#### DH 算法

![image.png](/images/posts/计算机基础-计算机网络-http-应用层/http-应用层-8.png)

A 和 B 是各自生成的公钥，因为离散对数运算具有交换律，所以下边两个都为 K，这个 K 就是秘钥。

可以看到，得到这个 K 需要，a 或 b。这两个知道一个就行，而客户端有a，服务端有b，他们都可以算出来这个密钥，根本不需要把这个往外传，不经过网络，这个私钥就很安全。黑客即使知道剩下的全部数据，由于离散对数的数学基础，在p是一个很大的质数时，现在的计算机是无法计算出来这个 a, b 的。

#### DHE 算法

DHE 对应 DH static ，static 已经被废弃了。

static 就是双方的私钥有一方一直不变，是静态的，比如服务端。这样的问题是，黑客可以收集多次通话的信息，暴力破解服务端的私钥，这就把所有的都看到了。不具有前向安全性。

DHE 就是每次会话都重新生成私钥。

#### ECDHE

就是针对 DHE 改进，因为离散对数计算效率不高，所以做了一下数学优化，改为了 ECC椭圆曲线特征，双方交换的东西也变成了椭圆曲线的参数。整体功能还是类似的，属于数学计算优化，不必深究。

### ECDHE 握手过程

这个大概的区别和之前差不多，也是先发随机数，选择套件。但是这次是选择ECDHE。

选了之后服务端就会先选一个椭圆曲线，基点啥的，这都是公开的。然后生成随机数作为私钥。再根据椭圆曲线计算出来公钥给客户端。

客户端也是类似的。双方最后都能算出来一个坐标 (x, y)，x是一样的。再把 客户端随机数 + 服务端随机数 + x 作为最后的密钥。

之后也是双方都试一下好用不，连接成功。

# RPC

rpc也是应用层协议，比HTTP出来的还要早。准确说，rpc不能算协议，只是描述远程调用，本地调用远程的方法。其具体实现比如gRPC才算真的协议。

一开始，rpc主要用于C/S架构，CS都是自己公司写做的一套东西，所以用rpc通信挺好。HTTP主要用于B/S架构，因为浏览器要访问各种服务器，就需要一套统一的资源。但是现在的产品很多都是既有BS又有CS，所以一般就用HTTP统一了。

因为RPC不需要考虑浏览器那些东西，在设计上可以使消息更轻，所以现在一般用在产品内部微服务的通信上。

上面的讨论一般基于现在广泛使用的 HTTP/1.1，其实HTTP2.0优化之后应该会比RPC好了，但是HTTP2.0是2015年才出来的。很难去取代RPC了，换了提升一点不值当的。

总结一下，就现在来说，客户端或浏览器调用服务器，一般用HTTP。服务器之间微服务调用，一般用RPC。

# WebSocket

TCP本身是全双工的，但是HTTP根据针对的场景，设计成了半双工的，如果需要服务端主动发消息给客户端，就有点麻烦，但是也能做。

用HTTP来实现服务器发消息给客户端的方式：

- 客户端轮询，这个好理解。
- 长轮询。就是请求的超时时间设置的大一点，服务端处理好了立马就发过来了。

- 这个适合于那种扫码登录的场景。

但是显然这两种方式其实还是客户端拉的。

所以才要用到另一个应用层协议 websocket，websocket是全双工的，适合于客户端和服务器之间需要频繁收发消息的场景，比如说网络游戏，实时聊天啥的。

websocket连接的建立过程是基于HTTP的，就是通过HTTP请求升级为websocket，但是建立连接之后就和HTTP没关系了。

这里要注意一点，就是这个粘包问题啊，这几个应用层的协议都是通过消息头 + 消息体的形式解决的，消息头里面存消息体的长度。

# URI 和 URL

URI 是同意组员标志符，就像是身份证，但是这算是个抽象的概念，就是说资源 id。

URL 是统一资源定位符，可以提供该资源的路径。URL 是一种具体的 URI，指明了如何 locate 这个资源。
