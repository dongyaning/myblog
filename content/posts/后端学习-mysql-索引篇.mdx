# 前传

这里我先写一下小哈书项目遇到的东西，后面再系统整理，可以融合一下。

最左匹配原则：**当你使用复合索引（Composite Index）时，MySQL 只能从索引的最左边列开始匹配，并且必须连续使用索引中的列，不能跳过中间的列。**

**​**

**底层原理：**

**B+树索引的存储结构是按列顺序排列的，也就是说，复合索引的第一列相当于是第一排序条件，第二列是第二排序条件，只有当第一列相同时，才会按照第二列排序。**

要特别注意的一点是：范围查询会中断最左匹配。**范围查询（>, &lt;, BETWEEN, LIKE 'abc%'）之后的列，无法再使用索引。**

```sql
SELECT * FROM user
WHERE name = 'Alice'
  AND age > 20
  AND city = 'Beijing';
```

这个语句 city 无法用到索引，原因是：前两个条件查询出来的记录中的city是无序的，city只在同一个name且同一个age的数据集合内部有序。

​

设计复合索引的最佳实践：

- 把选择性高的列放前面（不重复的）
- 范围查询放后面
- 索引包含了查询所需的字段，就不需要回表了

- 这个的原理是，索引和行记录不是存在一棵树上的，索引树的叶子结点存的是主键索引，如果要查询非索引字段，就必须要先查索引树，再拿查到的主键索引去查记录树。
- 主键的那个树叫聚簇索引，其它的叫二级索引。

​

验证：

```sql
EXPLAIN SELECT * FROM user WHERE name = 'Alice' AND city = 'Beijing';
```

​

B+树的数据查找过程：

就是分层的二分，一般来说B+树是很矮的，3层就可以存上亿的元素，因为B+树是一个多叉树，非叶子节点存的是范围拆分（对应的左子树数据范围），叶子结点存储行数据或主键。

每个结点内部都是二分查找

非叶子结点内部的结构大概如下：

```latex
+----------------+----------------+----------------+----------------+
| 指针 P₀        | 键值 K₁=100    | 指针 P₁        | 键值 K₂=200    | 指针 P₂
+----------------+----------------+----------------+----------------+

它的语义是：

所有 key < 100 的记录 → 走 P₀
所有 100 ≤ key < 200 的记录 → 走 P₁
所有 key ≥ 200 的记录 → 走 P₂,

K是有序存储的
```

当你查找 `key = 150` 时，流程如下：

### 步骤 1：将非叶子节点加载到内存

- MySQL 从磁盘读取这个页到内存（一次 I/O）
- 页中包含有序的键值数组：`[100, 200]`

### 步骤 2：在内存中对键值数组做 **二分查找**

- 目标：找到最大的 `K_i` 使得 `K_i ≤ 150`
- 二分过程：

- 中间是 `100`，`150 > 100` → 往右
- 下一个是 `200`，`150 &lt; 200` → 找到 `100`

- 结论：应走 `P₁`（`100` 对应的右子树指针）

### 步骤 3：递归进入子树

- 加载 `P₁` 指向的子节点
- 重复上述过程，直到叶子节点

# 索引分类

按数据结构可以分为 B+树索引，Hash索引和Full-text索引，InnoDB不支持Hash索引，一般B+树索引用的是最多的，也是默认的。

InnoDB会根据情况选择不同的列作为聚簇索引的键：

- 有主键，那就是主键
- 没有主键，就是第一个非NULL的唯一列
- 都没有，就生成一个隐式自增的id列，就是基础篇说的row_id

二级索引的叶子结点里面存的是主键值，查的就是二级索引和主键里面的，就不需要回表，就叫覆盖索引。

# 选择B+树的原因

对比法，B树，二叉树，Hash

## B+树 vs B树

先讲一下B树，B树和B+树最大的区别就是其非叶子结点也会存数据（存的是关键字的数据），也就是说B+树的非叶子结点只存关键字的索引，只做导航，B树也会存这些关键字的数据，如果查的就是这些用于分隔的关键字，就可以直接返回。但是会带来如下问题：

- **一个结点的大小是受限的**，不能太大，也不能太小，通常就是一页。如果存数据，存的索引就少了，树就会变高。而树变高就意味着磁盘IO变多，直接影响效率。
- B树的数据不只在叶子结点，所以对于范围查询，无法直接在叶子结点顺序扫描。而B+树的叶子结点是双向链表连接的，可以方便地做范围查询。

## B+树 vs 二叉树

这个很明显了，二叉树太高了。

## B+树 vs Hash

Hash做等值查询很快，但是范围查询直接就是不行，这是无法容忍的。

# 索引的适用条件和优化

索引虽然会提高查询效率，但是会增加物理存储空间，同时会影响增删改的效率，因为要维护索引结构。所以，索引不是万能的，要看情况来。

## 适用于索引的情况

- 字段有唯一性限制。
- 经常被用作where条件的字段。
- 经常用于Group By 和 Order By 的字段，避免查询内部排序。

## 不适用于索引的情况

- 查询条件用不到
- 大量重复字段
- 数据少
- 经常更新的字段，不要索引

## 索引优化

- 前缀索引，可以降低索引存储的内存空间
- 覆盖索引
- 主键自增

- 这个是因为B+树里面是按主键顺序存放的，考虑到物理空间，如果主键是自增的，就直接向页内追加即可，空间不够就开一个。但是如果是随机的，就很可能会插入到现有结构里面，造成页分裂影响效率。不自增也要整体是趋势增的，就像是雪花算法那种前面放时间戳来实现自增。

- NOT NULL

# 索引失效

#### 最左前缀，范围截断

![image.png](/images/posts/后端学习-mysql-索引篇/索引篇-1.png)

a >= 1 可以用到索引，说的其实也不是可以完全用到索引，而是优化器将a>=1拆成了a=1和a>1，a=1可以用，a>1不行。理论上a>1也行，但是实现复杂，没必要，mysql8+有类似机制。

#### 对索引使用函数或表达式

比如 select \* from t where YEAR(create_time) = 2023，这相当于不是用索引查的，是索引派生的另一个列，当然不行。

#### 隐式类型转换

VARCHAR不写引号，失效

这里要注意一点，Mysql在遇到字符串和数字转换的时候，都是把字符串转换为数字。而转换函数作用于索引，就会不生效，作用于值会生效。

因此：

```sql
select * from t_user where phone = 1300000001; // phone 为varchar，不会生效，因为会把
                                            // varchar 转换为数字，相当于对索引用函数
explain select * from t_user where id = '1';
// 这个的id 为int，会生效，因为把字符串转换为数字是对值的函数处理，不是索引。
```

# 数据页 & B+树的页级结构

## 数据页

数据页是数据读写的基本单位，结构如下：

![image.png](/images/posts/后端学习-mysql-索引篇/索引篇-2.png)

数据记录是链表形式存的，要遍历只能是顺序遍历，所以又弄了一个页目录，来检索业内数据。

这个页目录就是分组的形式，有很多槽，槽是顺序的，可以二分，每个槽指向每个组的最后一条记录，最后一条记录里面存着这个组有几条数据，这样就可以遍历了，但是要注意哈，这个链表是单链表，直接通过最后一条记录向前找不行，得先找到前面的槽，向后遍历即可。槽内顺序遍历即可，因为每个槽内的记录数是有限的，4-8个左右。

## B+树结构

![image.png](/images/posts/后端学习-mysql-索引篇/索引篇-3.png)

B+树的每个节点都是一个数据页。

查询流程就不说了吧，就是根据关键字范围来选择走哪个子树，在叶子结点根据页目录找到对应的组遍历即可。

# Count性能问题

**结论：count(\*) = count(1) > count(主键字段) > count(字段)**

其实，只要理解了这几个东西是在做什么，答案就出来了。

count(x) 返回的是 这个字段不为NULL的记录数。

而count(1) 返回的是 1 不为NULL的记录数，这当然是恒为true的，所以就是记录数，这也不需要判断，不需要回表，连记录数据都不需要读，拿一个记录，count+1，当然快，\*也是类似的，count(\*) = count(0)，和1是一样的。

这里还要注意一点哈：有二级索引的话就会用二级索引，因为二级索引比聚簇索引小，磁盘IO性能会更高，这是优化器决定的。

这里我**总结一下**：

上面说的那个结论的排序实际上要讨论一下

1.  没有where条件，对前面三个的优化就是会选择一个最小的二级索引，快在这里
2.  有where的时候就更明显了哈

注：如果没有二级索引，又没有where，其实都差不多。

建议用 count(\*)，这是标准写法，被优化的。

## 优化

1.  执行explain ，这个是近似估算的，不会真的去查询。
2.  额外表保存计数值

# 分页性能问题

```sql
select * from t where ... limit offset, size;
```

执行过程是**将前 offset + size 个数据取出来，忽略掉前 offset 个数据**，所以 offset越大性能越差。特别是当查询的数据是二级索引，还需要回表的时候，可能直接退化为全表扫描（优化器认为这么多回表还没扫描快）。

当offset很大，也就是页数很大的时候，叫做深度分页问题。这个问题现在来说是无解的，只能是针对某些场景的产品设计转化：

- 设计为只能一页一页地翻，那样的话可以记录一下上一次遍历到的id，之后使用 where id >= ... limit size 的方式来查找，这样可以用到索引，就没必要把前面的offset个数据都拿到了。
- 改变产品，大多数时候都没有必要搞这么多的分页，展示这么多，用户也不会看。
- 如果数据量少的话，就那么用吧，也是能行的。
