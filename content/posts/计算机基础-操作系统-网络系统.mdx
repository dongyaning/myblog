# DMA（Direct Momory Access，直接内存访问）

没有DMA时，IO过程：

- CPU对磁盘控制器发出指令。
- 磁盘控制器收到指令，准备数据，拷贝至其内部缓冲区，发出中断。
- CPU收到中断，亲自从磁盘控制器缓冲区中读取数据至寄存器，再放到内存。

这个过程是CPU全程主导的，数据搬运也是CPU干的，太浪费了。

所以就涉及了DMA，专门用来搬数据，解放CPU。

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-1.png)

早期DMA在主板上，现在IO设备越来越多，传输需求也不一样，所以一般IO设备都会内置DMA。

# 传统文件传输过程

场景：服务器发送文件数据到网络。

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-2.png)

简单说：需要经过 4次用户态和内核态上下文切换（因为两次系统调用，read 和 write） 和 4次数据拷贝。

1.  用户程序调用read。首先，DMA从磁盘文件读数据到内核空间。
2.  CPU将数据从内核空间拷贝到用户空间，给用户使用。
3.  用户程序调用write。CPU将数据从用户空间拷贝到内核的socket缓冲区。
4.  DMA 把数据从内核socket缓冲区拷贝到网卡缓冲区。

在高并发下，这种频繁的访问会影响系统性能。因此，要减少上下文切换和内存拷贝的次数。

对于这种文件传输的场景，显然 2，3 根本就是浪费，因为用户程序也不会对数据做什么改动。因此应该找到一种方式可以不把数据在内核和用户之间拷来拷去。那就是零拷贝。

# 零拷贝

**零拷贝定义：**

**在 I/O 操作中，避免 CPU 在用户态与内核态之间拷贝数据的技术。**

通常有两种实现：

- mmap + write
- sendfile

## mmap + write

前面之所以会将数据从内核态拷贝到用户态，是因为 read() 系统调用，那么我们不使用这个系统调用，用mmap替换read。

mmap 系统调用函数会直接把内核缓冲区里的数据【映射】到用户空间，不需要真的拷贝，相当于内核和用于程序共享那一片缓冲区。之后再通过write调用将内核缓冲区的数据拷贝到socket缓冲区中。最后，还是DMA负责将数据搬运到网卡缓冲区。

这个方式是 4次系统调用 + 3次内存拷贝（磁盘->内核缓冲区->socket缓冲区->网卡缓冲区）。

**这个方式只少了 内核-> 用户空间这一次拷贝**。

## sendfile

Linux 2.1 版本专门提供的发送文件的系统调用函数。

```c
ssize_t sendfile(int out_id, int in_fd, off_t *offset, size_t count);
```

因为这个只有一次系统调用，所以是 2次上下文切换 + 3次内存拷贝。

这个过程还可以优化，如果网卡支持 SG-DMA 技术，Linux 2.4 的 sendfile 系统调用对此做了优化。将缓冲区描述符和数据长度传到 socket 缓冲区，网卡的SG-DMA 就可以直接从内核缓冲区读取数据到网卡缓冲区，而不用传到socket缓冲区。

这个过程是 2次上下文切换 + 2次内存拷贝。

这就是零拷贝技术，解放CPU，不在内存层面去拷贝数据，CPU不参与搬运，所有的数据都是DMA在内存-IO设备之间传输的。可以把文件传输的性能提高至少一倍以上。

## pageCache

这个就是上面说的“内核缓冲区”，sendfile是依赖这个的，这也是个缓存。

注意：传输大文件的时候通常建议绕开pageCache，也就是不能用sendfile，但是不能说零拷贝用不了，得另外选择特定的方法。绕开的原因是大文件会占满缓冲区，但是它的命中率不高，会影响其他小文件的命中率。

# 网络通信模型

## 基本Socket模型

CS通信，必须得使用Socket编程，这里以TCP为例，说一下服务端的Socket编程过程。

1.  调用socket()，创建网络协议为IPv4，以及传输协议为TCP的Socket。
2.  调用bind()，给这个Socket绑定一个IP地址和端口。

3.  绑定IP：一个机器可以有多个网卡，每个网卡都有IP的。

4.  调用listen()，监听绑定的IP和端口。
5.  调用accept()，阻塞等待。

这个时候客户端调用 connect()，三次握手，当全连接队列不为空，accept()就会从全连接队列中拿出一个已经完成连接的Socket返回应用程序，后续数据传输都用这个Socket。

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-3.png)

## 多进程模型、多线程模型

多进程模型就是一个客户单对应一个进程，有一个父进程，来了新的客户端就fork一个子进程。

多线程模型可以利用线程池将连接处理轻量化。

但显然都无法应对高并发场景，一个连接对应一个线程，会导致线程爆炸。

## IO多路复用

用一个进程来维护多个Socket，一个进程虽然同一时刻只能处理一个请求，但是处理每个请求的耗时都在1ms，1秒内也能处理上千个请求，多个请求复用了一个进程，这就是多路复用，这种类似时间片的思想，也叫时分多路复用。

常见的系统调用：select、poll、epoll。

### select/poll

将已连接的Socket放到一个文件描述符集合，调用select将文件描述符集合拷贝到内核里，让内核来检查是否有网络事件发生。检查方式是遍历文件描述符集合，如果有事件就标记，然后将全量文件描述符拷贝给用户。用户再去遍历，看看哪些有事件。select 使用固定长度的BitsMap表示文件描述符集合，默认最大值1024。

poll和select类似，就是不用BitsMap，而是动态数组，突破了个数限制，但都属于是线性结构，只能遍历。

### epoll

优化：

- 内部用红黑树跟踪进程所有待检测的文件描述字。每次传入时只需要传入待检测的新的socket，插入到红黑树即可，减少了内存拷贝。
- 事件驱动，维护了一个链表记录就绪时间，只会返回给用户事件发生的文件描述符的个数，不需要遍历。

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-4.png)

## 边缘触发和水平触发

epoll的两种模式：

- 边缘触发：就是事件发生时，服务器只会苏醒一次，必须一次处理完。
- 水平触发：缓冲区的数据没处理完，就会一直苏醒。

epoll默认是水平触发，但是一般来讲边缘触发的性能更好，因为系统调用次数少，但建议搭配非阻塞IO使用。

## Reactor 和 Proactor

这个就是IO多路复用的面向对象实现。

Reactor（单 Reactor 单线程/进程）：

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-5.png)

- Reactor 对象监听和分发事件（连接就发给 Acceptor 并创建 Handler，业务就发给 Handler）
- Acceptor 处理连接
- Handler 处理业务

Reactor是非阻塞同步网络模式，Proactor是异步网络模式。（参考文件系统里说的同步/异步，非阻塞/阻塞）

Reactor 可以理解为 [ 来了事件操作系统通知应用进程，让应用进程来处理 ]，[Proactor 可以理解为来了事件操作系统来处理，处理完之后再通知应用进程 ]。

# 一致性哈希

## 场景

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-6.png)

负载均衡层的实现可以是轮询，或者是给实例一个权重，让某些节点承担更多的请求，这叫加权轮询。

但是**对于分布式系统，每个实例节点可能存的不是全量数据/服务，是被拆分开的**。就不能简单去轮询了，因为某些数据只有在某些节点才有，不能转发错了。

## 传统哈希

如通过 hash(key) % N，来确定具体的实例节点，会存在扩展性问题。【这个 key 是数据的 key，通过数据计算结点】。

如果要增加或者删除一个结点（N 变化），几乎所有的 key 的映射结果都会改变，导致大量数据需要重新分配和迁移，开销巨大！

## 一致性哈希

范围为 0-2^32 的哈希环：

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-7.png)

分别对 结点 和 数据 运用相同的哈希。

**将 某数据 与 顺时针方向第一个结点 匹配**。也就是说结点 A-结点 B 的数据，放到结点 B 上。

当增加一个结点时：

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-8.png)

影响的只有结点 B 的部分数据。

当删除一部分结点时：

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-9.png)

只是把原来在结点 A 的数据挪到结点 B 即可。

在理想均匀分布下，增删一个节点，**平均只需迁移** `**1/N**` **的数据**（N 为原节点数），远优于传统哈希的 `(N-1)/N`。

但是，一致性哈希并不能保证结点在环上的均匀分布，如果不均匀，就可能导致某些结点数据很多，某些结点数据很小。

因此，**一致性哈希算法解决了数据迁移量大的问题，但存在结点分配不均的问题**。

## 虚拟节点解决分配不均问题

一般来说，结点越多，分布越均匀，但是我们没有那么多实例。类似虚拟内存，我们对每个结点建立很多虚拟结点，再映射一层即可。

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-10.png)

虚拟节点还会提高系统的稳定性，节点变化时，会有不同的节点共同分担系统的变化。

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-8.png)

影响的只有结点 B 的部分数据。

当删除一部分结点时：

![image.png](/images/posts/计算机基础-操作系统-网络系统/网络系统-9.png)

只是把原来在结点 A 的数据挪到结点 B 即可。

在理想均匀分布下，增删一个节点，**平均只需迁移** `**1/N**` **的数据**（N 为原节点数），远优于传统哈希的 `(N-1)/N`。

但是，一致性哈希并不能保证结点在环上的均匀分布，如果不均匀，就可能导致某些结点数据很多，某些结点数据很小。

因此，**一致性哈希算法解决了数据迁移量大的问题，但存在结点分配不均的问题**。

## 虚拟节点解决分配不均问题

一般来说，结点越多，分布越均匀，但是我们没有那么多实例。类似虚拟内存，我们对每个结点建立很多虚拟结点，再映射一层即可。

虚拟节点还会提高系统的稳定性，节点变化时，会有不同的节点共同分担系统的变化。
