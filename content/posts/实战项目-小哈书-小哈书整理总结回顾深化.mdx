# 开发环境

## Docker

**Docker 的核心价值在于：\*\***标准化、隔离性、轻量级和可移植性\*\*。它极大简化了应用的开发、交付和运维流程，是现代软件工程中不可或缺的工具。

Docker 核心作用：

1.  **环境一致性**  
    将应用、运行时、系统工具、库等全部打包进容器，确保开发、测试、生产环境完全一致。
2.  **隔离性**  
    每个容器相互隔离，互不影响。即使一个容器崩溃，也不会影响其他容器或主机系统。
3.  **轻量级虚拟化**  
    与传统虚拟机（VM）不同，Docker 容器共享宿主机的操作系统内核，启动更快、资源占用更少。
4.  **可移植性**  
    一次构建，随处运行（Build Once, Run Anywhere）。无论是在本地、云服务器还是 Kubernetes 集群中，容器行为一致。
5.  **快速部署与扩展**  
    容器可以秒级启动/停止，便于实现自动化部署、弹性伸缩和持续集成/持续交付（CI/CD）。

假设你要部署一个 Python Web 应用，依赖 Flask 2.0 和特定版本的 Python。

- **不用 Docker**：  
  你需要在每台服务器上手动安装 Python、pip、Flask，还要处理权限、路径、版本冲突等问题。
- **用 Docker**：  
  你写一个 `Dockerfile`，定义好环境和依赖，构建出镜像。之后只需运行 `docker run your-image`，应用就跑起来了，无需关心底层系统。

### 使用

这里要注意，小哈书的容器都是 docker run 跑起来的，这样不能直接移植，得把这些命令记下来，写成 Dockerfile 重建镜像，别的机器直接 docker load + docker run，就可以重建环境了。

```latex
# 原始命令
docker run -d -p 8080:80 -v ./html:/usr/share/nginx/html nginx

# Dockerfile
FROM nginx
COPY ./html /usr/share/nginx/html
EXPOSE 80

# 构建并导出
docker build -t my-nginx .
docker save -o my-nginx.tar my-nginx

# 新机器
docker load + docker run
```

# KV 键值对服务

为什么类似数据读取不用 mysql，而是 cassandra。

场景特点（笔记内容、评论内容）：

- 写多读少

- **“笔记和评论的写入吞吐量极高、写入压力大，且写入模式对数据库架构挑战更大；而读取虽然总量大，但可通过缓存极大缓解，对底层存储的压力相对可控。”**

- 数据量大
- 查询模式固定
- 不需要复杂事物、JOIN、外键
- 允许最终一致性
- 对高可用、水平扩展要求极高。

**为什么 mysql 不适合？**

- mysql 为“强一致性+复杂查询”而生，核心优势在于：

- ACID 事务
- 多表 JOIN
- 外键约束
- 复杂 WHERE + 排序 + 聚合

- 写入瓶颈：单点写入
- 大字段

- 占用过多缓存，影响缓存效率。
- 行过大，影响 B+树索引性能，最直接的就是聚簇索引，叶子结点一行会占的很大，存的就会变少，很可能要分好几个页，影响性能。
- 大 binlog，主从复制延迟增大。

- 水平扩展复杂
- 高可用依赖外部机制

**为什么 cassandra 合适？**

- 分布式宽列存储，为“高可用+高写入+水平扩展”为生，核心设计目标：永远可写，即使部分节点宕机。
- 顺序写，写入性能强。
- 水平扩展。

**总结**

- **MySQL 不适合笔记/评论**，不是因为它“不好”，而是因为它的**设计目标与这类数据的访问模式不匹配**；
- **Cassandra 适合**，是因为它**为高写入、高可用、水平扩展而生**，正好命中内容型数据的核心需求；
- **根本差异源于 CAP 权衡和数据模型设计**：MySQL 选 CP（强一致），Cassandra 选 AP（高可用）；
- **混合架构（MySQL + Cassandra）** 是大型内容平台的**理性选择**，兼顾一致性、性能与成本。

这个地方写的比较乱，我总结一下：

1.  MySQL 要支持事务等特性，写入的时候需要写入日志什么的，而且因为要支持复杂查询，像是 B+树这种结构对于数据刷盘一般还是随机写。MySQL 在高并发写入时，InnoDB Buffer Pool、Redo Log、索引更新可能成为瓶颈。**相比之下，cassandra 的写入性能要强得多，全部是顺序写 CommitLog+MemTable**。
2.  cassandra 水平扩展简单方便，加机器自动扩容。而 MySQL 需要分库分表，复杂度高，且存在一定的查询难题需要去解决，如跨分片查询，迁移数据。
3.  cassandra 无主架构，无单点故障。MySQL 主从架构，主库宕机需切换。cassandra 可用性更高。
4.  cassandra 宽列存储，数据模型灵活；MySQL 的表结构是固定的。

同时，cassandra 也存在不支持复杂查询、事务能力弱、删除墓碑问题、运维复杂度高等问题。

**没有银弹**。现代系统往往是 **“Cassandra 存数据 + ES 做搜索 + Redis 做缓存”** 的混合架构。
