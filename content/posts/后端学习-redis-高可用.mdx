# 主从复制

为了实现高可用，某一服务器宕机也能继续提供服务，设置多个服务器，一个主服务器，多个从服务器。

主服务器负责读写数据，从服务器一般只进行读，也就是所谓的读写分离。当主服务器执行了新的写操作后，会将写操作同步至从服务器，从而实现主从一致。

![image.png](/images/posts/后端学习-redis-高可用/高可用-1.png)

## 主从服务器之间的第一次同步

### 命令

```shell
# 服务器 B 执行这条命令
replicaof <服务器 A 的 IP 地址> <服务器 A 的 Redis 端口号>

// 执行完之后，服务器B就会变为服务器A的从服务器。
```

第一次同步可以分为三个阶段：

1.  建立链接、协商同步
2.  主服务器同步数据给从服务器（传输RDB文件)
3.  主服务器发送新写操作命令给从服务器。

主从服务器在完成第一次同步后，双方会维护一个TCP连接。并且这个链接是长连接，目的是避免频繁链接带来的开销。后续主服务器可以通过这个TCP连接来将写操作同步给从服务器。

## 分级

从服务器还可以有从服务器，这样可以分担主服务器的压力。因为如果从服务器很多，每个都需要主服务器生成全量同步数据，那么主服务器的压力就会很大。

我们可以通过在从服务器执行如下命令，使其作为目标服务器的从服务器：

```shell
replicaof <目标服务器的IP> 6379
```

![image.png](/images/posts/后端学习-redis-高可用/高可用-2.png)

## 增量复制

这个的场景是：如果网络断开，主服务器就无法同步写操作给从服务器，后面即使再连上，断开的这段时间写的数据也不一致了。redis2.6之前使用的策略是从服务器重新连接之后，再重新发送全量数据，但是这样显然性能开销太大。

后面做了改进，重连后只发送断开期间写的操作。实现方式是主服务器中有一个环形缓冲区，平时主服务器发送给从服务器数据时，也会发到缓冲区一份。再加上主从服务器都有一个偏移量，可以通过这个偏移量去缓冲区里面找，把需要的数据发过去即可。但是显然，如果断开时间长，那么需要的数据可能被覆盖(因为是环形的)。如果出现这种情况，那么就只能发送全量数据。所以我们要尽量把缓冲区设置的大一些。一般不小于 重连时间 \* 主服务器每秒操作大小。

可以通过修改配置文件调整缓冲区大小：

```shell
repl-backlog-size 1mb
```

## 总结

总结来看，就是三种模式：

- 全量复制
- 基于长连接的命令传播
- 增量复制

## 扩展

主从复制框架中，过期key如何处理？

A：主结点删除之后，模拟一个del操作发送给从服务器即可。

# 哨兵

redis 2.8版本提供。

## 哨兵机制的作用

当主结点挂了，哨兵机制可以自动监控，重新选举主结点并通知从节点主结点变更。

## 哨兵的工作机制

哨兵是一个特殊状态运行的结点，主要有三种动作：

- 监控：监控主结点状态，判断主结点是否正常运行。
- 选主：当主结点挂了之后，选出新的主结点。
- 通知：更换主结点之后通知其它结点变更消息。

下面一个一个来看。

### 监控

哨兵节点每秒（可配置）会向主从结点发送一次PING，以此来判断节点的运行状况。如果节点没有在规定时间内给哨兵响应，那么哨兵就认为其“主观下线”。这个主观客观下线是只针对主结点的，因为要考虑到因为网络原因误判的情况，哨兵将主节点判断为主观下线后，会向哨兵集群的其它哨兵发信息，让所有的哨兵投票，如果票数超过阈值，就认为主节点客观下线。那么就要选举新的主节点了。

### 选出哨兵Leader主导主从切换

哨兵Leader也需要选举，候选人就是第一个判断主结点为客观下线的哨兵。然后让其它的哨兵投票，只有候选人可以把票投给自己。

需要满足两个条件成为Leader：

1.  拿到半数以上的票。
2.  票数 >= 配置文件中的 quorum。

建议quorum的值设置为哨兵个数的一半下取整 + 1， 哨兵节点的个数为奇数。

### 主从故障转移的过程

![image.png](/images/posts/后端学习-redis-高可用/高可用-3.png)

主从故障转移操作包含四个步骤：

1.  在已下线的主节点属下的所有从节点里面，挑选出一个从节点，将其切换为主节点。
2.  让主节点属下的所有从节点修改复制目标，修改为复制新主节点。
3.  将主节点的IP地址和信息，通过发布者/订阅者机制通知给客户端。
4.  继续监视旧主节点，当这个旧主节点重新上线时，将它设置为新主节点的从节点。

#### 选出新的主节点

选择一个状态良好的节点发送 SLAVEOF no one 命令，将这个从节点切换为主节点。

选择新主节点时，要首先排除网络不好的从节点。判断网络状态好坏可以根据从节点中记录的down-after-milliseconds属性。这个属性标识了主从节点超过一定时间限制没有连接上的情况发生的次数。如果这个次数超过了10次，那么就可以认为这个从节点的网络不好，排除即可。

排除了网络不好的从节点后，根据三个排序规则进行排序，这三个是递进的关系，前面的相同才会比较下一个。

1.  优先级。从节点都有一个优先级，可能是根据其硬件配置或人为计划偏好等设置。
2.  复制进度。就是从节点同步数据的进度，进度快的优先。
3.  ID号。如果前面两个都一样，就选择ID小的。

在确定了新的主节点人选之后，哨兵Leader发送SLAVEOF no one 命令给新的主节点，并监控其回复直到其自称master为止。

#### 将从节点指向新主节点

向原主结点所属从节点发送 SLAVEOF 新主节点 命令即可。

#### 通知客户主节点变更

通过发布者/订阅者模式实现，每个哨兵都会发布很多频道，客户去订阅，接收消息。

#### 将旧主结点变为从节点

监视旧主节点，重新上线之后，哨兵集群向它发送 SLAVEOF 命令，变为从节点。

## 哨兵集群的组成

在搭建哨兵集群时，只需要填写主节点信息。哨兵节点之间通过Redis的发布者/订阅者机制（\_\_sentinel\_\_:hello频道）来相互发现。并通过主节点获取从节点信息，对主从节点进行监控。

# Cluster 集群

这个相当于是 **数据分片 + 分片内主从复制 + 分片内置故障转移（类似哨兵的功能）**。

结构可概括如下：将全部数据分片放到几个主节点里面，每个主节点又配备几个从节点，主从复制+故障转移保证高可用。

这个主要是解决了性能问题，单个节点内容量过大肯定会影响性能的，不管是RDB快照还是故障转移，效率都和数据量直接相关。

## Cluster 分片

核心机制：哈希槽（Hash Slot）

```python
# 伪代码
def key_to_slot(key):
    # 注意：Redis 会先对 key 取 {tag}（见下文）
    crc = CRC16(key)          # 返回 0 ~ 65535
    slot = crc % 16384        # 0 ~ 16383
    return slot
```
