Garbage Collection, GC

Java堆是垃圾收集器管理的主要区域，因此也被称作GC堆。

内存管理里面已经说过了，现在的GC一般都是基于分代垃圾收集算法的，所以Java堆被划分为了几个不同的区域。

新生代，老年代，永久代（元空间）。

# 内存分配和回收策略

大多数情况下，对象优先在新生代中Eden区分配，当空间不足时，发起一次Minor GC。

## 大对象直接进入老年代

需要大量连续内存空间的对象，如字符串、数组。

优化策略，避免将大对象放入新生代，从而减少新生代的垃圾回收频率和成本。

## 长期存活的对象进入老年代

刚创建放入Eden，一轮Minor GC之后放入survivor，在survivor中每熬过一轮年龄就增加1岁。当年龄达到阈值（这个阈值不一定是15，看收集器的，一般是15，也有的比如说CMS是6）

## 空间分配担保

就是在进行Minor GC之前，先要确保当前老年代可用的最大连续空间是否大于新生代中对象的总大小。如果大于的话，一定是安全的。（因为极端情况，可能会把所有新生代的对象都放入老年代）。如果不安全，在JDK 6 UPDATE 24之前和之后的处理不同。

之前：可以设置是否可以冒险，如果可以冒险且老年大最大连续空间大于历次晋升到老年代对象的平均大小，那就执行Minor GC，否则执行 Full GC。

之后：如果老年代最大连续空间大于新生代对象总大小或者历次晋升的平均大小，就会进行 Minor GC，否则将进行 Full GC。

# 死亡对象判断

## 引用计数法

无法解决循环引用问题

## 可达性分析

从GC Root判断对象可达性。

GC ROOTS：

- 虚拟机栈(栈帧中的局部变量表)中引用的对象
- 本地方法栈(Native 方法)中引用的对象
- 方法区中类静态属性引用的对象
- 方法区中常量引用的对象
- 所有被同步锁持有的对象
- JNI（Java Native Interface）引用的对象

# 引用类型

## 强引用

一般写的 new 出来的就是强引用，引用存在，就不会被GC。

## 软引用

```java
// 软引用
String str = new String("abc");
SoftReference<String> softReference = new SoftReference<String>(str);
```

如果内存空间足够，就不会被GC。如果空间不够了，就算还可达也可以被GC。

## 弱引用和虚引用

弱引用：就算内存空间足够也会被GC。

虚引用：等于没有，任何时候都可能被GC。

虚引用主要用来跟踪对象被垃圾回收的活动。其必须和一个引用队列关联。当垃圾回收器准备回收一个对象时，如果发现它还有虚引用，就会在回收对象的内存之前，把这个虚引用加入到与之关联的引用队列中。程序可以通过判断引用队列中是否已经加入了虚引用，来了解被引用的对象是否将要被垃圾回收。

# 无用类判断

同时满足：

- 所有实例被回收。
- 加载该类的加载器被回收。
- 对应的java.lang.Class对象没有被引，无法通过反射访问该类。

# 垃圾收集算法

内存回收的方法论。

## 标记清除算法

基线，后续基于此改进。

两阶段：标记、清除。先扫描一遍，不需要清除的都标记，之后对没标记的清除。

问题：

1.  效率。
2.  内存碎片。

## 复制算法

分成两块，只用一块。每次把还活着的复制到另一块，再清除一块。

问题：

1.  可用内存变小。
2.  老年代对象数量大，复制性能变差。

## 标记整理算法

就是先标记，再把存活的都挪到前面，清理后面的。

效率也不高。

## 分代收集算法

就是分为新生代、老年代啥的。然后每个代选择合适的算法，如新生代用复制算法，老年代用标记清除或标记整理。

# 垃圾收集器

内存回收的具体实现。

没有最好的垃圾收集器，根据场景选择。

JDK默认：

JDK 8：Parallel Scavenge 新生代 + Parrallel Old 老年代

JDK 9-22：G1

## Serial

单线程，运行的时候暂停其它所有工作线程，"Stop The World"。

新生代：标记复制。老年代：标记整理。

## ParNew

Serial 收集器的 多线程版本，其余一样。

## Parallel Scavenge

和ParNew差不多，提供了一些配置，关注吞吐量，注意CPU资源。JDK8 默认。

## CMS（Concurrent Mark Sweep）

关注并发、获取最短回收停顿时间。第一个真正意义的并发收集器，与用户线程并发工作。

标记清除，会产生内存碎片。

在JDK9被废弃，JDK14被移除。

## G1

JDK9开始的 默认垃圾收集器。

主要目标是解决传统GC在大堆场景下的痛点。

核心理念：**在用户指定的停顿时间内，尽可能多地回收垃圾，而不是一次性清空所有垃圾**。

### 核心机制

1.  堆内存划分为大小相等的Region，默认2048个。

1.  Region类型：Eden、Survivor、Old、Humongous（大对象，单独占一个或多个连续Region）

1.  Remembered Sets

1.  每个Region有一个Rset，记录哪些其他Region引用了本Region的对象。

1.  Collection Sets

1.  每次GC，G1选择一组最有回收价值的Region（垃圾比例高，回收成本低）

1.  GC流程

| **阶段**            | **是否 Stop-The-World** | **说明**                                            |
| ------------------- | ----------------------- | --------------------------------------------------- |
| **Initial Mark**    | ✅ 是（短暂）           | 标记 GC Roots 直接引用的对象，**伴随一次 Young GC** |
| **Concurrent Mark** | ❌ 否                   | 并发标记整个堆的存活对象（类似 CMS）                |
| **Remark**          | ✅ 是（较短）           | 完成最终标记，处理并发期间的变化                    |
| **Cleanup**         | ✅ 是（极短）           | 统计各 Region 垃圾比例，排序，为 Mixed GC 做准备    |
| **Mixed GC**        | ✅ 是（可控）           | 回收部分 Young + 部分 Old Region（CSet）            |

### G1 vs CMS

首先，G1和CMS都是面向低延迟场景的垃圾收集器，但它们的设计思路和实现机制有很大不同。

CMS基于标记清除，主要在老年代工作，并发执行，会产生内存碎片，对CPU资源敏感。

G1从JDK7引入，JDK9之后成为默认的垃圾收集器，它将堆内存划分为多个大小相等的Region，没有固定的新生代老年代边界。基于标记整理，无内存碎片，通过Remembered Sets实现Region间的引用跟踪，支持部分回收。

提供可预测的停顿时间模型，可通过如下参数设置：\-XX:MaxGCPauseMillis。

总结一句话：

**CMS 是“并发标记-清除”的老年代回收器，有碎片问题且已废弃；G1 是基于 Region 的新一代 GC，通过“优先回收垃圾最多区域”实现可预测低停顿，无碎片，是现代 JVM 的首选。**
