Redis 不同于 Memcached 的很重要一点就是，Redis 支持持久化，而且支持 3 种持久化方式:

- 快照（snapshotting，RDB），**默认方式**
- 只追加文件（append-only file, AOF）
- RDB 和 AOF 的混合持久化(Redis 4.0 新增)

- 一个文件中，RDF保存基本数据，AOF保存持久化期间的增量数据。
- 混合持久化相当于是对AOF的优化，不算是一个独立的持久化方式，只是对AOF的优化！！！
- **生产环境建议开始 AOF + 混合持久化**。
- **混合持久化只发生在AOF重写的时候！！！**

如果**同时开启RDB和AOF**，redis会生成 .rdb 和 .aof 两个文件，但是重启时，只会用AOF文件恢复数据！

# AOF（Append Only File）

实际上就是将写操作记录到日志里（日志文件在硬盘中），如果宕机了啥的可以通过日志恢复缓存。

![image.png](/images/posts/后端学习-redis-持久化/持久化-1.png)

策略是先执行完毕写操作，再写日志。写日志也是先写到缓冲区里，再写到硬盘里。

这里执行写操作和写日志是两个动作，就不可避免地会出现问题：

- 数据丢失风险，写完就宕机了，数据就丢失了。
- 主进程堵塞，性能问题，写日志也要占用进程。

一般有三个策略：

1.  Always，每次执行完写操作就写到硬盘。数据丢失风险低，堵塞风险高。
2.  EverySec，每秒写一次。折中。
3.  No，只写入缓冲区，由操作系统决定写入时机。数据丢失风险高，堵塞风险低。

具体根据业务需求选择即可。

## AOF 重写机制

当AOF文件过大的时候，恢复起来就很耗时了，这时候就需要重写。

重写的本质是去重，就是再新建一个文件，把当前redis里面的每个最新值建立一个set记录。最后把原来的日志文件覆盖了。比如 set name xm set name xw， 重写之后第一条就没了。

### AOF 后台重写

重写操作还是很费时间的，所以新开一个子进程来执行该过程。这里创建子进程可以利用操作系统的写时复制，避免加锁。创建子进程之后，调用fork系统调用，会复制一份父进程的页表，共用一份物理空间。但是这个是只读的，写的时候就会触发写时复制，将物理空间分离（只会分离写过的地址）。

这里会存在一致性问题，就是在重写期间，主进程里面又改数据了，那就不一致了。redis使用重写缓冲区解决这个问题，开启重写之后，启用重写缓冲区。每次写数据的时候，不只向数据缓冲区里面写，也向重写缓冲区里面写一份。等子进程重写完了，通知主进程的时候。再把重写缓冲区中的内容追加到新的AOF文件里面。完成重写过程。

这里Redis7.0更新了Multi Part AOF，把AOF分成了 base AOF、inc AOF和history AOF。解决重写期间，增量数据要全部放到内存的问题，可以直接把增量数据写到inc AOF。

## AOF 校验机制

对于AOF文件，不会通过校验和校验，而是逐条解析文件的命令来验证文件的有效性。

对于混合持久化模式，前面是RDB快照部分，这个会计算其CRC64校验和 以及 RDF部分之后，AOF部分之前记录的校验和是否相等，之后再逐条解析校验AOF部分。

# RDB快照

RDB快照也是记录日志，和AOF的区别是：

- AOF是记录操作。
- RDB是直接记录数据（二进制）。

- 所以RDB在恢复的时候要比AOF快，因为省去了执行操作的时间。

## RDB快照的使用方式

两个命令：save 和 bgsave，区别是是否在主线程进行。save 在主线程，bgsave会新建子进程。

可以通过配置文件的方式来指定多长时间执行一次bgsave。

要注意的是，**bgsvse是全量快照**，即每次快照都会把内存中的全部数据都放到磁盘中。所以RDB是一个很重的操作，不能执行太频繁，所以显然丢失数据的风险就会更高。这也是RDB的缺点。

还有一个大问题，就是在使用子进程RDB快照的过程中，如果主线程修改了，会触发写时复制，在快照期间主线程修改的数据是没有办法同步到子进程中的。如果这个时候宕机了，那么刚刚写的数据就丢了。

所以RDB的优点是恢复速度快，缺点就是频率不好把握。

- 如果频率太低，那么宕机时就可能丢失更多数据。
- 如果频率太高，那么就会影响性能（全量快照）。

# 混合AOF、RDB快照（Redis4.0 引入的AOF的优化，不算是新的持久化方式）

目的是为了综合两者优点：

- AOF可以借助重写缓冲区实现执行**过程中修改的持久化**。
- RDB的**恢复速度比较快**。

方法就是在fork子进程后，**不把RDB数据存到RDB的日志里面，而是存到AOF的日志里面**。缓存完了之后再把重写缓冲区的内容追加到AOF文件里面，替换原来的AOF文件。

**也就是说，AOF文件的前半部分是RDB的二进制内容，后半部分是追加的AOF操作记录。**

# RDB和AOF对比、选择

总的来说，RDB可读性不强，特定格式，新老版本可能会不兼容，但是文件很小，恢复速度快，适合用于数据备份。

AOF体积大，恢复慢，但是可读性强，可以用于分析。安全性比RDB好，因为RDB的执行频率不能很高，AOF可以一点一点追加写。

**综上：**

- 数据丢失一点可以接受，建议RDB。
- 不建议单独使用AOF，创建一些RDB备份挺好。
- 安全性要求高可以同时开启 RDB + AOF持久化/混合持久化。

# 大Key如何影响持久化

首先对于AOF，要分情况来说，因为AOF有三种方式，Always, EverySec, No. 其中Always因为是主线程操作，影响比较大，可能会阻塞主线程。

同时，大Key会加速AOF重写的发生。重写时可能发生阻塞：

- fork 复制页表，如果页表很大，可能会阻塞。
- 写时复制时，所占空间太大也会阻塞。

所以尽量在设计阶段就规避大Key。
