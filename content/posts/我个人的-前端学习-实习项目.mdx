针对新简历的问题：

**先说总的回答策略**  
如果面试官问：

“你在七牛这段实习主要做了什么？”

不要一上来逐条念简历。  
更好的回答方式是先给一个总括，再挑 2 个重点展开。

你可以这样答：

“我在七牛这段实习，主要做的是灵矽 App 里和智能硬件接入相关的核心链路。比较有代表性的工作有三块：第一块是设备接入流程，包括蓝牙配网、扫码添加设备和异常兜底；第二块是设备接入后的智能体绑定与权限一致性；第三块是多语言和资源配置化改造。这里面我做得最深的是设备接入和默认智能体绑定这两块。”

这段话的好处是：

- 有全局观
- 不会一上来就碎
- 主动引导面试官追问你准备好的点

## 1\. 第一条怎么答

简历原文大意是：

_参与智能硬件 App 核心链路建设，围绕设备发现、蓝牙配网、扫码绑定与设备筛选规则下发，完善多步骤接入流程中的异常回退、空结果兜底与流程跳转逻辑。_

面试官大概率会追问：

- 设备接入流程具体是怎样的？
- 你做了哪些部分？
- 这里最难的点是什么？
- 为什么要做异常回退和兜底？

### 你可以这样答

“这个模块本质上不是单个页面，而是一条多步骤设备接入链路。用户要先选择设备接入方式，比如蓝牙配网或者扫码绑定；如果走蓝牙链路，还会经历设备扫描、筛选、连接、WiFi 配置、提交结果这些步骤。我当时主要做的是这条链路里的前端流程控制和异常处理。

一个比较典型的问题是，蓝牙扫描和筛选并不是稳定成功的。我们后来加了一个由后台动态下发的设备筛选规则，App 在扫描前先请求这个规则，再决定展示哪些设备。但这里有两个容易卡死用户的场景：一个是请求筛选规则超时，另一个是规则过严导致筛出来 0 台设备。我的处理方式是，前者超时后直接回退为‘展示所有设备’，后者除了提示用户检查设备状态外，还提供一个‘显示所有设备’按钮，避免用户被错误规则卡在流程里。”

### 这一段里你体现的能力

你答完以后，面试官会感受到你有这些能力：

- 你理解的是“链路”，不是单页面
- 你有异常场景设计意识
- 你不是只写 happy path
- 你能把产品体验和技术逻辑连起来

### 再往下追问“你具体改了哪些代码”

你就往真实点落：

- 状态管理：步骤流转、回退
- 接口请求：筛选规则下发
- UI 兜底：空状态、显示所有设备
- 流程控制：跳过配网、返回逻辑

你不用把文件名背出来，但你脑子里要知道是：

- 页面层
- store 层
- 蓝牙协议/工具层  
  这三层在配合

## 2\. 第二条怎么答

简历原文大意是：

_参与设备绑定后的智能体管理流程改造，支持默认智能体按系统语言自动匹配，并梳理公开/私有智能体的详情读取、编辑入口与模板应用逻辑，提升前后端业务一致性。_

这条其实很适合面试，因为它比“做页面”更像“做业务建模”。

面试官可能会追问：

- 默认智能体按系统语言匹配是什么意思？
- 为什么这是个问题？
- 公开/私有智能体的权限边界具体是什么？
- 模板误创建是怎么回事？

### 你可以这样答

“这个模块的背景是，设备添加完成后，用户往往还要再去绑定一个智能体。我们后来做了一次流程改造，希望设备添加后能自动绑定一个默认公开智能体，减少用户首次使用成本。

这里看起来像一个小功能，但实际牵涉两个复杂点。第一个是语言匹配。最开始系统绑定默认智能体时，使用的是界面语言，但后来发现这并不总是准确，比如用户界面语言和设备系统语言不一致时，会匹配到错误的公开智能体。后面我们把这条链路改成基于系统语言去匹配，逻辑上更符合用户真实语境。

第二个复杂点是公开/私有智能体的边界一致性。我们发现系统里存在一种情况：公开智能体可以绑定，但某些接口又不允许读取详情，或者前端遗留了编辑入口，导致用户能点进去但不能真正修改。还有一个问题是模板应用，在编辑智能体时套用模板，前端错误地调用了创建接口，导致变成新建一个智能体，而不是更新原智能体。后来我做的工作就是把这些入口、接口和权限边界梳理清楚，让‘可绑定、可读取、不可随意编辑’这几个行为统一起来。”

### 这里的加分点

这段回答很适合字节、腾讯这类会问“业务一致性”的面试官。

你体现的是：

- 不是只会写接口调用
- 能发现系统行为不一致
- 能理解“权限边界”和“业务模型”
- 知道前端问题很多时候不是 UI 问题，而是业务语义不一致

### 面试官如果追问“你怎么判断边界该怎么设计”

你可以答：

“我的判断标准主要是从用户视角和系统语义出发。比如公开智能体本质上是可复用资源，不是用户私有可编辑对象，所以它应该允许被读取和绑定，但不应该暴露出误导性的修改入口。也就是说，前端入口、接口返回能力和后端权限控制要保持一致，不然用户感知会很混乱。”

这句话会显得你思路很清晰。

## 3\. 第三条怎么答

简历原文大意是：

_推动 App 资源配置化与国际化能力建设，将教程视频、说明书等资源由前端硬编码迁移为后台动态接口下发，并参与多语言界面适配。_

面试官可能会追问：

- 为什么要把资源从硬编码迁移成后台下发？
- 这里的国际化你做了什么？
- 这件事的技术价值是什么？

### 你可以这样答

“这块一开始看起来不是很难，但我觉得挺能体现工程意识。之前 App 里的教程视频和说明书链接是前端硬编码的，这会导致一个问题：只要资源地址变化，或者新增语言版本，就要跟着发版。这个成本其实挺高的，而且对国际化支持也不灵活。

后来我们把这部分改成后台动态下发。也就是 App 带着系统语言去请求接口，后台如果有对应语言版本就返回对应资源，没有的话就回退到默认版本。这样改完以后，文档和教程的更新不再强依赖 App 发版，前端也从硬编码资源路径变成消费配置型接口。

在这个基础上，我还参与了韩语、阿拉伯语、哈萨克语这些语言的界面适配。对我来说，这件事的价值不只是‘加几份翻译’，而是把资源分发和语言适配一起纳入配置化体系，后面扩展会更顺。”

### 这里最好的点

这一条很适合讲“工程化”和“配置化思维”。

你体现出来的是：

- 不是只接一个需求
- 你在降低系统后续维护成本
- 你理解国际化不只是翻译文本，还包括资源分发策略

### 面试官如果追问“国际化除了翻译你还考虑了什么”

你可以答：

“除了文本翻译，还要考虑资源版本、回退策略、系统语言和界面语言的区别，以及不同语言下内容是否真的可用。比如有些资源没有本地化版本时，要不要回退英文，这种就是产品逻辑和技术实现一起要考虑的。”

## 4\. 第四条怎么答

简历原文大意是：

_参与跨平台兼容性优化，处理安卓录音格式、语言标签映射异常及功能展示条件控制等问题。_

面试官可能会追问：

- 安卓录音格式为什么会有问题？
- 你具体怎么处理的？
- 功能展示条件控制是什么意思？

### 你可以这样答

“这块主要是音色克隆相关功能。问题的根源是，后端训练接口期望的是 WAV，但 uni-app 在安卓设备上实际录出来的格式不是这个，导致整条训练链路在真实设备上会失败。另外还有一个问题是语言标签，后端同步回来的语言标识不符合 App 侧实际使用的格式，导致即使训练成功，前端也没法正常消费。

我做的工作，一部分是协助把这条链路的问题定位清楚，包括平台录音格式差异和后端返回字段不一致；另一部分是在前端侧补充展示条件控制，比如某些功能只在中文界面或非鸿蒙系统下展示，避免把当前还不稳定或不支持的能力暴露给用户，造成错误体验。”

### 这段回答的关键

重点不是“我修了一个安卓 bug”，而是：

- 你理解跨平台的真实差异
- 你知道功能不可用时不应该硬露给用户
- 你会用“能力边界控制”来保证可用性

这就比较成熟。

## 最好准备的“总问题”

你这段实习，面试官大概率还会问一句：

**“你觉得这段实习里最能体现你成长的点是什么？”**

你可以这么答：

“我觉得最大的成长，是我开始从‘做功能’转向‘看链路和一致性’。比如设备接入这块，如果只是做页面，其实很容易只做 happy path，但真实用户一定会遇到扫描不到设备、规则错误、流程中断这些问题；智能体那块也是，如果只看单个接口，很容易忽略前端入口、后端权限和业务语义不一致的问题。实习里我比较明显地体会到，前端不只是把页面写出来，而是要把一条业务链路做完整、做稳。”

这段很适合作为总结。

# linx

linx 是一个基于 uni-app + Vue3 + Pinia 的跨端应用，面向智能设备接入和后续智能体绑定场景。核心价值在于把‘用户登录 -> 设备发现 -> 蓝牙连接 -> WiFi 配网 -> 配网结果确认 -> 后续智能体绑定’这条链路做成稳定、可恢复、可跨平台运行的闭环。这个项目里我参与得最深、也最能体现前端工程能力的模块，是蓝牙配网流程。

我在这个项目里**做得比较深的是蓝牙配网模块**。这个模块表面上看是一个多步骤页面，但本质上是一个带状态机特征的长链路交互系统。用户先扫描设备、再连接蓝牙、拉取设备可见的 WiFi 列表、输入密码下发配置，最后再等待设备返回结果。这个过程中真正难的点不在页面切换，而在于流程状态一致性、蓝牙链路不稳定、不同平台差异，以及异常情况下怎么恢复。

1\. 我当时做了一个取舍。这个流程跨了多个页面片段和异步阶段，如果把状态分散在组件内部，会很容易出现步骤回退后状态残留、连接断开后 UI 不一致、序列号错乱这些问题。所以我把它抽成了一个独立的流程状态管理层，而不是让每个组件各自维护自己的局部状态。这样做的好处是步骤切换、异常重置和结果回写都有统一入口，代价是需要自己维护 listener 和状态同步，但对于这种长链路流程，这种集中式管理更稳。

2\. 我比较在意的一点是不要把协议细节揉进组件里。因为蓝牙配网不是普通表单提交，它涉及设备指令、分包数据、结果监听、重连和超时。我把这部分抽到了协议层，组件只关心‘现在拿到了什么状态、给用户展示什么反馈’。比如 WiFi 列表的解析和去重是在协议层做的，页面只拿结果渲染。这样做的好处是协议逻辑可复用、UI 更干净，后续如果协议变化也不会大面积改页面。

3\. 这个模块另一个难点是异常恢复。蓝牙链路天然不稳定，所以我不是只做 happy path，而是把连接丢失、扫描为空、提交超时、用户返回上一步这些场景都当成主流程来设计。比如连接丢失后，我会重置协议状态并自动重启配网流程；提交阶段如果等待时间过长，会给用户‘可能卡住’的提示；如果 WiFi 扫描失败，除了重试还提供手动配置兜底。我的想法是，硬件接入场景里用户最怕的是‘不知道现在发生了什么’，所以前端不只是发请求，更要承担流程可解释性和恢复能力。

除了设备接入，我**还参与了登录鉴权链路**。前端这边做了统一请求封装和 token 生命周期管理，包括 access token、refresh token、过期前预刷新，以及免鉴权接口和鉴权接口的区分。我的关注点不是单纯把 token 存起来，而是避免过期时出现并发刷新、无限重试和错误跳转不一致的问题，所以把 token 管理抽到了 store 层，把请求处理和登录态恢复统一收口。
