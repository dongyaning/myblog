# SQL执行流程（MYSQL架构）

![image.png](/images/posts/后端学习-mysql-基础篇/基础篇-1.png)

分为两个部分：Server层 和 存储引擎层。

**Server 层负责建立连接、分析和执行 SQL**。还包括内置函数，如日期、时间等。

**存储引擎层负责数据的存储和提取**。实现索引数据结构等。

#### 连接器

基于TCP。

空连接不会一直被占用，达到了配置时间就会被断开，

类似HTTP，也存在短连接和长连接，长连接可能会占用内存过高，造成异常重启。

解决方法可以是：

- 定期断开长连接
- 客户端执行大操作后主动重置连接

#### 查询缓存

就是对于查询操作，会先去查缓存，每次数据库更新就清空缓存。

MySQL 8.0 版本直接将查询缓存删掉了（Server层的），比较鸡肋。

#### 解析

就是对SQL语句进行词法分析和语法分析。

#### 执行

三个阶段：预处理、优化、执行

- 预处理

- 判断表名、字段是否存在
- 将 \* 换为全部字段

- 优化

- 将执行方案确定下来，比如有多个索引，确定用哪一个

- 执行

- 和存储引擎交互执行SQL语句。
- 执行的过程是以记录为单位的，也就是说是一行一行来的。
- 考虑三种情况：

- 主键索引查询

```sql
select * from product where id = 1;
```

- id 是主键，且为等值查询，所以优化器使用const进行查询。
- 执行器首先调用read_first_record函数指针指向的函数，让存储引擎去定位符合条件的第一条记录。查询到了之后给Server层，Server层判断一下是否符合条件，符合就返回给客户端。
- 因为是const，找到一个就返回了。

- 全表扫描

```sql
select * from product where name = 'iphone';
```

- 这个 name 是没有索引的，所以使用 all 的方式来查询。
- 也是调用 read_first_record，一条一条判断，符合条件就返回给客户端，不符合就跳过。所以说这个过程是以记录为单位的。

- 索引下推

```sql
select * from t_user where age > 20 and reward = 100000;
```

- 范围查询会中断最左匹配原则（联合索引 (age, reward)）
- 如果没有索引下推，查询过程就是 age>20的记录 -> 主键id -> 回表 -> 判断reward
- 但是因为reward也在索引里面，所以判断的时候不需要回表
- 有索引下推就是：age>20的记录->主键id和reward -> 判断reward -> 满足条件再回表

#### 存储引擎

MySQL 当前默认存储引擎是 InnoDB，这是唯一一个事务性存储引擎，只有 InnoDB 支持事务。

其它的还有 MyISAM、Memory、Archive、NDB 等等。

**MyISAM 和 InnoDB 对比：**

- InnoDB 支持行级别的锁粒度，MyISAM 不支持，只支持表级别的锁粒度。
- MyISAM 不提供事务支持。InnoDB 提供事务支持，实现了 SQL 标准定义了四个隔离级别。
- MyISAM 不支持外键，而 InnoDB 支持。
- MyISAM 不支持 MVCC，而 InnoDB 支持。
- 虽然 MyISAM 引擎和 InnoDB 引擎都是使用 B+Tree 作为索引结构，但是两者的实现方式不太一样。
- MyISAM 不支持数据库异常崩溃后的安全恢复，而 InnoDB 支持。
- InnoDB 的性能比 MyISAM 更强大。

对于咱们日常开发的业务系统来说，你几乎找不到什么理由使用 MyISAM 了，老老实实用默认的 InnoDB 就可以了！

MySQL 存储引擎采用的是 **插件式架构** ，支持多种存储引擎，我们甚至可以为不同的数据库表设置不同的存储引擎以适应不同场景的需要。**存储引擎是基于表的，而不是数据库。**

# MSQL行记录存储（InnoDB）

```sql
SHOW VARIABLES LIKE 'datadir';
```

有三种文件格式：

- db.opt，存储当前数据库的默认字符集和字符校验规则。
- table_name.frm，表结构，每张表一个。
- table_name.ibd，表数据，每张表一个，这个是可配置的，也可以共享，默认是分开。
- 在MYSQL8.0中，已经把opt和frm文件删除，继承到innodb的数据字典中。

## .idb文件结构：

![image.png](/images/posts/后端学习-mysql-基础篇/基础篇-2.png)

分为 表、段、区、页、行 五级结构。

- 行，数据的存储单位，后面重点介绍。
- 页，数据的读取单位，默认每页大小 16KB，页是InnoDB磁盘管理的最小单元。
- 区，为了使B+树中逻辑相邻的页物理也相邻，将随机IO变为顺序IO，表中数据量大时，为某个索引分配空间不再按照页，而是区，每个区 1 MB，64个 16KB。
- 段，一般分为数据段，索引段和回滚段。

- 索引段，存放B+树非叶子节点的区的集合
- 数据段，存放B+树叶子节点的区的集合
- 回滚段，存放回滚数据的区的集合

## InnoDB行格式

四种行格式，分别是 Redundant, Compact, Dynamic, compressed

Redundant 比较过时，了解即可。Compact是紧凑的行格式，是比较重要的基线，重点讲解。Dynamic和compressed都是基于Compact改进的。

### COMPACT行格式

![image.png](/images/posts/后端学习-mysql-基础篇/基础篇-3.png)

分为 记录的额外信息 和 记录的真实数据 两个部分。

#### 额外信息

**变长字段长度列表：**

比如说VARCHAR，数据类型的长度是不确定的，所以说要存储下数据实际占的内存大小。当数据表中没有变长字段的时候，行格式就不会有这个部分了。

**NULL值列表：**

将NULL值作为真实数据存入比较浪费空间，所以使用二值bit位按逆序标记所有可能为null的字段是否为null。但是最少一个字节，8个位，不够就补0即可。这个也类似，不是必须的，没有可能为NULL值的列就不需要这个列表。

**记录头信息：**

包含很多信息，如：

- detete_mask，标识此数据是否被删除，这相当于是数据库层面实现的status.
- next_record，下一条记录的位置。所以记录与记录之间是通过链表组织的。这里要注意，next_recored指向的是下一条记录的[记录头信息]和[真实数据]之间的位置，再加上前面两个东西都是逆序存储的，所以向左读就是记录头信息，向右读就是真实数据，比较方便。
- record_type，表示当前记录的类型，0表示普通记录，1表示B+树非叶子节点记录，2表示最小记录，3表示最大记录。

#### 真实数据

包括我们定义的表字段和三个隐藏字段，row_id，trx_id，roll_pointer。

- row_id，非必须，一般情况下是没有的，只要指定了主键或者唯一约束列，就不会有这个字段，6字节。
- trx_id，事务id，必须，表示这个数据是由哪个事务生成的，6字节。
- roll_pointer，此记录上一个版本的指针，必须，7字节。

## varchar(n) 中n最大取值

MYSQl规定除了TEXT，BLOBs等大对象类型，其他所有的列（一行）总字节数不超过65535。

varchar(n) 这个n 说的是字符数，所以说n多大跟字符集有关系，如ascii就是一对一。

要注意的是，这个65535是包括变长字段长度列表和null值列表的。

对于多个字段的表，那么就是全部的单个极限值加起来要在65535字节的范围内。
