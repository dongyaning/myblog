# 面试常见问题与回答整理（小红书/高并发项目）

---

## 问题1：笔记详情为什么要使用本地缓存？本地缓存快，那用本地缓存不就行了，为什么还要用 Redis？怎么实现存放的都是热点数据，或者说怎么做到冷热数据的分离？

**回答：**  
本地缓存作为 L1 缓存，可以实现极致的访问速度；Redis 作为 L2 缓存，提供更大的容量（相较于本地缓存，速度略差）；它们是互补关系，外加数据库作为最后的海量数据持久层。  
本地缓存内存相较 Redis 容量较小，仅存储一些大 V 的数据（比如粉丝数大于 1w 的）。  
冷热数据分离可以通过热点 key 探测，实现动态续期：将热数据存储在本地缓存（永不过期），常规数据存储在 Redis（常规过期策略）。

## 问题2：分布式 ID 的 QPS 2w+，面试官对这个好像很感兴趣，回答只是整合了美团 Leaf 源码，这样子说面试官好像不太满意。

**回答：**  
不能光说“整合了”，得说明：

- 通过前期选型，对比了各大主流分布式 ID 框架（如 Snowflake、UUID、数据库自增、Leaf 等），说出各自的优缺点；
- 最终基于业务需求（如趋势递增、高并发、无单点）选型了 Leaf；
- 自己通过 JMeter 压测，列出机器配置（如 4C8G），证明单机就能达到 2w+ QPS。

## 问题4：缓存命中率 90% 是怎么测出来的？

**回答：**  
90% 的缓存命中率是通过：

- 在代码中埋点监控（如记录缓存命中/未命中次数）；
- 测试团队在预发布环境进行压测；
- 线上环境长期观察后，综合计算得出的一个数据。

## 问题5：小哈书项目你们是按照什么原则拆分的这些服务模块？

**回答：**  
拆分原则包括：

1.  **单一职责原则**：按业务边界拆分，每个服务只负责一个独立业务，如笔记服务、评论服务等；
2.  **高内聚、低耦合**：功能相关的代码应放在同一个服务中；
3.  **按变更频率拆分**：高频变更服务（如促销活动）独立部署；
4.  **按承接流量划分**：高 TPS 服务（如计数服务）单独拆分，便于后续扩容。

## 问题6：存储评论不也可以先存在 Redis 之后再存数据库吗？这样不更快吗？为什么引入 Cassandra？还有，Nacos 本身就可以共享用户 ID，不需要在拦截器去透传。

**回答：**

1.  先存 Redis 再批量同步到 DB 是一种方案，但：

- 小红书量级下，缓存大量短文本会占用大量 Redis 内存；
- Redis 即使开启 RDB/AOF，仍有数据丢失窗口，不适合做评论这种强一致性要求的数据存储；
- 关系型数据库处理高频短文本写入存在性能瓶颈。

2.  Header 透传用户 ID 方案：

- 轻量、性能高、代码简单；
- Nacos 共享会增加网络开销和延迟，且存在数据更新延迟导致服务间用户 ID 不一致的风险。

---

## 问题7：用户的关注与取关，用户关系服务是怎么设计的？怎么保证两个表（关注表与粉丝表）内容一致？如果是大 V 的情况，做了哪些处理应对高并发？

**回答：**

- 定义了关注表（from_user_id → to_user_id）与粉丝表（to_user_id ← from_user_id），内容对称；
- 通过数据库事务保证写入一致性；
- 后续可通过订阅 Binlog 实现异步补偿，进一步保证最终一致性；
- 对于大 V：采用 Redis 缓存 + 二级缓存，结合冷热数据分离策略（如只缓存 TOP 大 V 的关注/粉丝列表）。

## 问题8：分布式 ID 都用来生成什么 ID 的？

**回答：**

- **用户 ID**：使用号段模式（Segment）；
- **笔记 ID**：最初考虑雪花算法（含时间戳，便于冷热分离），但因点赞系统采用咆哮位图（Roaring Bitmap）仅支持 32 位整数，遂也改为号段模式；
- 两种模式生成效率基本无差异。

---

## 问题9：点赞系统怎么设计的？为什么改为咆哮位图了？

**回答：**  
演进过程：

1.  **Set 结构**：内存占用高；
2.  **布隆过滤器**：内存降低，但存在误判，需二次查库；
3.  **咆哮位图（Roaring Bitmap）**：既能高效判断是否点赞，又大幅降低内存占用，且无误判。

---

## 问题10：咆哮位图的机制，为什么有你说的这些优点？

**回答：**  
咆哮位图（Roaring Bitmap）是一种高效压缩位图：

- 将 32 位整数空间划分为 $2^&#123;16&#125;$ 个块（每个块含 $2^&#123;16&#125;$ 个整数）；
- 每个块根据稀疏程度选择存储方式：稀疏用数组，稠密用位图；
- **优点**：内存占用低、位图运算（并/交/差）速度快。

---

## 问题11：计数表是单独设计的，用伪代码写一下 SQL 表，笔记表和计数表怎么分开存储的？

**回答：**

- **笔记表（note）**：存储笔记基本信息（note_id, user_id, title, content_uuid, create_time...）；
- **计数表（note_stats）**：存储高频更新字段（note_id, like_count, comment_count, collect_count...）；  
  **目的**：避免频繁更新笔记表导致行锁竞争，提升写性能。

## 问题12：笔记服务怎么用 CompletableFuture 并发调用下游服务的？伪代码实现。

**回答：**

```java
CompletableFuture<UserInfo> userFuture = CompletableFuture.supplyAsync(() -> userService.getUser(userId));
CompletableFuture<List<Comment>> commentFuture = CompletableFuture.supplyAsync(() -> commentService.getComments(noteId));
CompletableFuture<List<Like>> likeFuture = CompletableFuture.supplyAsync(() -> likeService.getLikes(noteId));

CompletableFuture.allOf(userFuture, commentFuture, likeFuture).join();

NoteDetail detail = new NoteDetail();
detail.setUser(userFuture.get());
detail.setComments(commentFuture.get());
detail.setLikes(likeFuture.get());
```

## 问题13：笔记里面，文本内容单独存储在 Cassandra，为什么？笔记表里文本内容存储的是什么？

**回答：**

- MySQL 存储长文本性能差（需两次磁盘 IO，且影响主表查询）；
- Cassandra 是分布式 NoSQL，适合海量非结构化数据，写入性能高；
- 笔记表中存储的是 **content_uuid**，作为 Cassandra 的主键。

---

## 问题14：存储在 Cassandra 里不也是两次磁盘 IO 吗，有什么区别？

**回答：**

- Cassandra 是分布式数据库，数据分片存储，支持并行读写；
- 写入为顺序写（Append-only），性能极高；
- 设计目标就是高吞吐、高可扩展，相比 MySQL 在非结构化数据场景优势明显。

---

## 问题15：为什么不用笔记 ID 作为 Cassandra 的 key？

**回答：**

- 笔记 ID（如雪花 ID）含时间戳，可能导致写入热点（集中在某节点）；
- UUID 随机性好，可均匀分布，避免热点；
- 隐藏 ID 生成规则，增强数据隐私性。

---

## 问题16：笔记的点赞系统是怎么设计的？伪代码中怎么没有体现？

**回答：**

- 使用咆哮位图存储每个笔记的点赞用户 ID 集合；
- 点赞：将 user_id 加入位图；取消：移除；
- 查询是否点赞：检查 user_id 是否在位图中；
- 伪代码聚焦主流程，点赞作为独立模块未展开。

## 问题17：为什么用 HTTP REST 接口，而不是 Dubbo 等 RPC 协议？

**回答：**

- 项目初期注重开发效率，HTTP 简单、易调试、团队上手快；
- 未追求极致性能，后续用户量上来可改造为 RPC；
- “先验证业务，再优化架构”是合理策略。

---

## 问题18：为什么不建议直接使用 Spring 的 `@Async`？

**回答：**

- 简单场景可用，但需自定义线程池（禁用默认 SimpleAsyncTaskExecutor）；
- **主要问题**：自调用（this.method()）会绕过代理，导致异步失效；
- 灵活性差，难以监控、限流、重试。

---

## 问题19：数据对齐服务作为兜底方案，如何保证日增量表数据可靠？为何不直接在计数服务加幂等？

**回答：**

1.  MQ 消费时写入日增量表，加唯一索引防重复；
2.  计数服务本身也应做幂等，但仅靠幂等可能漏判（如时钟漂移导致时间戳重复）；
3.  **兜底方案**：数据对齐服务每日凌晨跑批，补偿缺失数据，实现最终一致性。

---

## 问题20：如果用 ShardingSphere 分库分表，怎么分比较合适？

**回答：**

- **用户表**：user_id 哈希取模；
- **笔记表**：复合分片 — 一级按 user_id，二级按 create_time；
- **关注表**：按 from_user_id 分片，用一致性哈希；
- **粉丝表**：按 to_user_id 分片；
- **点赞/收藏表**：按 user_id 分片，一致性哈希。

---

## 问题21：BufferTrigger 机器挂了，内存中的消息怎么办？

**回答：**

- 内存数据丢失，但计数场景允许一定误差；
- 由数据对齐服务兜底，凌晨做增量对齐；
- 类似 RocketMQ 异步刷盘机制：为高吞吐牺牲强一致性，业务可接受。

## 问题23：点赞操作完 Redis ZSet 后发 MQ，若消息发送失败，如何保证缓存与 DB 一致？

**回答：**

- 封装 MQ 发送组件，支持重试（如 1s/2s/4s 三次）；
- 若仍失败，将失败消息存入 DB；
- 定时任务捞取失败消息，异步重发，保证最终一致性。

---

## 问题24：为什么选 RocketMQ，而不是 RabbitMQ/Kafka？

**回答：**

1.  与 Spring Cloud Alibaba 无缝集成；
2.  吞吐量高于 RabbitMQ，适合高并发业务；
3.  Java 开发，便于定制；
4.  支持事务消息、延迟消息、消息过滤等业务友好特性；
5.  Kafka 更适合大数据/流处理，非典型业务系统首选。

---

## 问题25：百万粉丝大 V 的粉丝列表缓存失效，导致缓存击穿，如何解决？

**回答：**

- 不推荐分布式锁（高并发下线程阻塞严重）；
- **方案**：

- 大 V 缓存永不过期（或超长 TTL）；
- 结合热点 key 探测 + 动态续期；
- 冷热分离：TOP 10% 大 V 数据常驻缓存，普通用户常规过期。

---

## 问题26：如何保证计数消费的幂等性？

**回答：**

- 方案1：DB 中记录 message_id，消费前查重；
- 方案2：布隆过滤器 + Redis + MySQL：

- 布隆判断不存在 → 直接入库；
- 存在 → 查 Redis/DB，避免重复消费；

- 布隆误判由数据对齐服务兜底，保证最终一致性。

---

## 问题27：RocketMQ 发消息删本地缓存没删干净怎么办？

**回答：**

1.  **补偿机制**：消费失败时记录日志，异步重试删除缓存；
2.  **兜底策略**：设置较短 TTL（如 1~5 分钟），靠自动过期实现最终一致性。
